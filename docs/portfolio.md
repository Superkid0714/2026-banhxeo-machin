# 반쎄오 축제 부스 주문 서비스

실제 축제 부스에서 고객 접수부터 입금 확인·조리·픽업 안내·이력 관리까지 지원한 주문 서비스다. **개인 개발 프로젝트이며 개발 기여도는 100%**다. 직접 구현·배포한 서비스를 태블릿 2대로 운영하며 확인한 요구를 UI와 서버 기능에 반영했다.

## 핵심 성과: 둘째 날 평균 완료 처리시간 약 71% 감소

> 실제 운영에서 발견한 접수 병목과 관리자 업무를 개선했다. 유사한 인력·숙련도 조건에서, 둘째 날 재료 배송 지연으로 제작 지연이 있었음에도 주문 접수→완료 처리 평균 시간은 26.9분에서 7.9분으로 약 71% 감소했다.

| 운영 지표 | 첫째 날: 10월 6일 | 둘째 날: 10월 7일 | 비교 |
| --- | ---: | ---: | --- |
| 주문 접수→완료 처리 평균 | 26.9분 | 7.9분 | **약 71% 감소** |
| 같은 시간의 중앙값 | 29.1분 | 8.0분 | 약 72% 감소 |
| 같은 시간의 90백분위수 | 39.0분 | 15.4분 | 약 61% 감소 |
| 15분 초과 주문 비율 | 49/58건·84.5% | 6/49건·12.2% | **72.2%p 감소** |
| 30분 초과 주문 비율 | 26/58건·44.8% | 1/49건·2.0% | **42.8%p 감소** |
| 음식 1개 주문 평균 | 47건·26.42분 | 42건·7.42분 | **약 71.9% 감소** |
| 문자 재발송 요청 | 0회 | 20회 | 추가 기능의 실제 사용 확인 |
| 서버 기록 주문 수 / 음식 수량 | 58건 / 70개 | 49건 / 56개 | 음식 수량 20% 감소 |
| 서버 기록 결제 확인 금액 | 419,000원 | 336,000원 | 매출 증가 성과로 표현하지 않음 |

**성과 요약:** 접수→완료 처리 평균은 약 19.0분·70.6% 감소했고, 중앙값은 72.4%, 90백분위수는 60.5% 감소했다. 30분 초과 주문 비율도 44.8%에서 2.0%로 42.8%p 낮아졌다. 음식 1개 주문끼리 비교해도 평균 71.9% 감소 방향을 확인했다. 둘째 날 픽업 재안내 요청은 20회 사용됐다.

15분·30분은 사전에 정한 SLA가 아닌 사후 탐색 기준이다. 초과 비율은 유효한 완료시간이 있는 주문을 분모로 계산하고 정확히 15분·30분인 주문은 해당 초과 건수에 넣지 않는다. `%p`는 비율의 절대 차이이며 시간 감소율 `%`와 구분한다. 같은 표본에서 파생한 지표를 여러 독립 실험의 성공 횟수로 세지 않는다.

**기록 기반 결과:** 서버의 전체 잔존 완료 이력 58건·49건을 날짜별로 비교했다. 기능은 중복 주문 단계 제거·접수 후 홈 복귀, 관리자 재발송·연락처 조회·상태 흐름 정리 등으로 개선했다. 재발송 20회는 요청 이력이며 전달 성공이나 고객 방문 20회를 의미하지 않는다.

**운영자 확인 조건:** 인력·숙련도는 이틀간 비슷했고, 둘째 날 재료가 늦게 도착해 제작 지연이 있었다. 배송 지연의 정확한 구간·분수와 접수 이후 측정 시간에 포함된 정도는 기록되지 않았다.

**해석 범위:** 약 71%는 개선을 진행한 이틀의 관측 차이다. 둘째 날 음식 수량 감소, 완료 버튼의 처리 시점 차이, 기능별 적용 시점은 통제하지 않았으므로 전체 감소를 서비스 개선의 단독 인과 효과로 환산하지 않는다. UI 입력시간이나 순수 조리시간을 71% 단축한 지표로 사용하지 않는다. [산출 기준·비교 한계](operations-record.md#이틀-운영의-수치-비교)를 함께 제공한다.

**가설과 검증:** 운영 경험을 “불필요한 고객 조작·관리자 업무 마찰을 줄이면 주문 처리 흐름이 빨라질 것”이라는 가설로 재구성했다. 사전 등록 실험은 아니다. 짧은 기록 제외, 음식 1개 주문, 공통 접수 시간대 비교에서도 감소 방향이 유지됐다. 다만 주문은 같은 대기열을 공유하고 관찰일도 두 날뿐이어서 독립표본 검정의 작은 p값으로 서비스 개선의 인과 효과를 확정하지 않았다. [통계 분석과 다음 검증 설계](statistical-review.md)에 정의·가정·탐색값을 공개한다.

## 주요 문제와 해결

### 1. 접수 병목을 고객 흐름 개선으로 연결

실제 장사 중 불필요한 선택·확인·완료 단계가 접수 흐름을 늘린다는 피드백을 받았다. 이용 방법·추가 최종 확인·제출 직후 완료 화면을 없애고, 접수 성공 후 홈으로 돌아가 다음 고객을 받을 수 있게 했다. 개인정보 동의와 계좌 확인은 목적이 달라 별도 화면으로 유지했다.

화면 수만 줄이기보다 공유 기기에서 한 고객의 접수 종료와 다음 고객의 시작까지 설계했다. 변경된 동작은 확인했지만 고객의 UI 입력시간 자체의 전후 감소율은 측정하지 않았다. 접수 이후 완료 처리까지의 71% 감소와는 다른 지표다.

### 2. 재방문·연락 업무를 관리자 기능과 서버 처리로 지원

문자를 한 번 보냈어도 바로 찾아오지 않는 고객이 있어 수령완료 단계에서도 픽업 재발송을 지원했다. 직원이 고객에게 연락하고 주문을 대조할 수 있도록 인증된 관리자에게 전체 전화번호와 검색을 제공했다.

재발송 버튼과 함께 진행 중 중복 요청 차단, 발송 접수·전달 결과 구분, 문자 작업 lease 검사를 구현했다. 고객 API의 마스킹과 저장 전화번호 암호화는 유지했다. 관리자 상태·문자 연계와 처리 완료 주문의 보관도 정리했다.

### 3. 태블릿 2대의 동시 사용에서 서버 정합성 유지

두 태블릿이 독립된 화면을 사용하므로 한쪽에서 처리한 주문을 다른 쪽이 이전 상태로 조작할 수 있다. 서버가 주문·설정 버전을 검사해 오래된 요청을 거부하고 화면에서 안내 후 최신 상태를 조회하도록 했다. 주문번호·재고·주문 변경은 SQLite 트랜잭션으로 처리하고, 현장 주문은 요청 키, 예약은 예약 ID로 중복을 방지했다.

예를 들어 A에서 결제 확인 후 B의 화면 갱신 전에 같은 버튼을 누르면 B의 오래된 요청을 거부한다. 이 순서는 코드 설명용 예시이며 당시 실제 버튼·오류·발생 횟수는 확인되지 않았다. 5초 폴링의 표시 지연과 서로 다른 새 요청 키의 주문을 자동 합치지 않는 한계도 문서화했다.

### 4. 현장의 대기시간 질문을 예측과 검증으로 연결

주문 접수부터 준비·완료 처리까지의 기록, 접수 당시 앞선 음식 수량, 새 주문 수량을 사용하는 비음수 최근성 가중 회귀를 구현했다. 최신 최대 80건과 반감기 120분을 사용하고 새 접수의 대기량을 반영하며 완료 기록이 바뀌면 재학습한다.

처음에는 넓은 범위와 모델 지표를 노출했지만 관리자가 필요한 것은 고객에게 안내할 시간이었다. 화면은 “지금 주문하면 약 ○분” 한 줄로 바꾸고 검증 지표는 내부에 유지했다. 화면 단순화와 모델 정확도는 구분했다.

## 운영 결과와 검증

2026-11-26 대조 기준 전체 운영 실적은 **109건·128개·766,000원**이다. 주문 서버 API의 완료 기록 107건·126개·755,000원과 이전 운영자가 별도 확인한 예약 수령 2건·2개·11,000원을 구분해 합산했다. API에 이미 포함된 예약은 다시 더하지 않았다. 비용·순이익은 계산하지 않았고 이 실적을 특정 개선의 효과로 귀속하지 않는다.

동일 기준일의 모델은 과거 순차 검증 20건 평균 절대 오차 3.5분, 비교 기준인 최근 10건 평균 방식 4.0분이었다. 실제 접수 당시 예측과 완료를 비교한 최근 20건의 운영 오차는 3.6분이었다. 시간 보장이나 모든 주문의 최대 오차를 뜻하지 않는다.

TypeScript·운영 빌드와 도메인·복구·주문·예약·문자·모델·인증·배포·API 자동 테스트 **48건**을 검증했다. 테스트는 로컬·임시 저장소·모의 문자 전송으로 수행하며 실제 태블릿·무선망의 모든 장애를 재현한 것은 아니다.

분석 스크립트의 별도 자동 테스트 4건은 한국 날짜·소요시간·백분위수·누락·역전·개인정보 필드 차단과 15분/30분 초과 경계·분모·음식 1개 표본을 확인한다. 런타임 48건과 분석 검증의 범위를 구분한다.

## 운영 이후 발견한 개선과 배운 점

행사 이후 실제 흐름과 코드를 대조해 미사용 단계·컴포넌트 삭제, 판매 가능 여부의 설정 전용 조회, 보드의 전체 이력 제외 조회, 800ms 고정 지연 제거, 예약 코드 계약 통일을 구현했다. 11월 26일 소스 `da381a3`에 반영하고 로컬 검증했으며 운영 서버에는 아직 재배포하지 않았다.

운영 경험을 통해 고객 화면의 완료가 다음 고객의 시작과 연결된다는 점, 문자 발송과 고객 방문·전달은 다른 사건이라는 점, 두 화면의 일치보다 서버의 최종 상태 검증이 중요하다는 점을 배웠다. 이후에는 준비 완료와 실제 전달 시각을 분리하고, 기기별 충돌 기록·접수시간·예측 오차 분포를 측정해 개선 효과를 검증할 계획이다. 이는 향후 과제이며 구현 완료로 기록하지 않는다.
