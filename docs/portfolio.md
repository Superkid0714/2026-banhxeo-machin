# 반쎄오 축제 부스 주문 서비스

축제 부스에서 사용할 주문 서비스를 혼자 개발하고 배포했다. 태블릿 2대로 이틀간 운영하면서 고객 접수와 직원 업무에서 생긴 불편을 수정했다. 고객·관리자 화면, 서버, DB, 인증, 문자·예약 연동, 대기시간 예측과 배포까지 맡았다. **개발 기여도는 100%다.**

| 항목 | 내용 |
| --- | --- |
| 기술 | React, TypeScript, Node.js 22, SQLite, Solapi, Railway |
| 운영 | 태블릿 2대, 이틀간 총 109건·128개·766,000원 |
| 대표 결과 | 접수→완료 처리 평균 26.92분→7.92분, 약 71% 감소 |
| 품질 확인 | 런타임 테스트 48건, 분석 테스트 4건 및 실제 주문 기록 재계산 |

## 운영하면서 바꾼 것

### 주문을 끝낸 고객이 다음 고객의 접수를 막지 않도록

주문 화면에 이용 방법 선택과 추가 확인, 제출 후 완료 화면이 남아 있었다. 장사 중 이 단계들이 필요 없다는 걸 알게 됐고, 제출에 성공하면 처음 화면으로 돌아가도록 바꿨다. 개인정보 동의와 입금 계좌 확인은 각각 따로 두었다. 고객이 해야 할 확인은 남기면서 다음 고객에게 기기를 넘기는 데 필요한 조작을 줄였다.

### 고객에게 다시 연락할 수 있도록

픽업 문자를 한 번 보냈다고 고객이 바로 찾아오지는 않았다. 완료 단계에서도 픽업 문자를 다시 보낼 수 있게 했고, 직원이 연락처를 확인할 수 있도록 관리자 카드·상세·이력에 전체 번호와 검색을 넣었다. 둘째 날에는 재안내 요청이 20회 기록됐다.

재발송 중에는 중복 요청을 막고, 문자 서비스의 접수와 실제 전달 상태를 나눠 표시했다. 전체 전화번호는 인증된 관리자에게만 제공하고 고객 응답의 마스킹과 저장 시 암호화를 유지했다.

### 태블릿 2대의 동시 사용을 미리 대비

태블릿 2대로 운영할 예정이어서 같은 주문의 중복 처리나 오래된 상태 덮어쓰기를 먼저 고려했다. 화면의 중복 클릭 방지만으로는 다른 기기의 요청까지 막을 수 없기 때문에 서버에서 주문·설정 버전을 검사하도록 했다. 오래된 요청은 거부하고 최신 상태를 다시 조회한다. 주문·번호·재고는 SQLite 트랜잭션으로 함께 저장하며, 현장 주문은 요청 키, 예약은 예약 ID로 재접수를 막는다.

이틀간 태블릿 2대로 운영하면서 중복 처리나 상태 덮어쓰기로 인한 장애를 겪지는 않았다. 문제가 생긴 뒤 복구한 사례보다, 예상한 위험을 설계에 반영하고 실제 운영에 사용한 경험이다. 두 화면에서 같은 결제 확인을 누르는 상황은 보호 방식을 설명하는 예시다.

기기별 409 응답과 충돌 횟수를 별도로 집계하지 않았으므로 ‘충돌 0건’이나 ‘장애율 0%’를 계측한 결과는 아니다. 서로 다른 새 요청 키로 제출한 주문을 자동으로 합치는 기능도 없다.

### 대기시간을 물으면 답할 기준을 만들기

접수부터 준비·완료 처리까지의 기록에 현재 앞선 음식 수량과 주문 수량을 반영하는 회귀 모델을 구현했다. 최신 최대 80건을 쓰고 최근 기록에 더 높은 가중치를 줬다. 완료 기록이 바뀌면 다시 학습하고, 신규 주문에는 당시 예측을 저장해 실제 시간과 비교한다.

처음에는 예측 범위와 학습·검증 정보를 모두 보여줬다. 직원에게 필요한 건 지금 주문할 고객에게 안내할 시간이어서 화면은 **“지금 주문하면 약 ○분”** 한 줄로 줄였다. 모델 진단 지표는 내부에 남겼다.

## 이틀간의 결과

서버에 남은 완료 기록 107건을 한국 접수 날짜로 나눠 비교했다. 시간은 **주문 접수부터 첫 준비·수령완료 이력까지**다. 이번 기록은 모두 수령완료 이력을 사용했다.

| 지표 | 첫째 날: 10/6 | 둘째 날: 10/7 | 변화 |
| --- | ---: | ---: | --- |
| 평균 | 26.92분 | 7.92분 | 19.00분·70.6% 감소 |
| 중앙값 | 29.09분 | 8.03분 | 72.4% 감소 |
| 90백분위수 | 38.95분 | 15.38분 | 60.5% 감소 |
| 15분 초과 | 49/58건·84.5% | 6/49건·12.2% | 72.2%p 감소 |
| 30분 초과 | 26/58건·44.8% | 1/49건·2.0% | 42.8%p 감소 |
| 음식 1개 주문 평균 | 47건·26.42분 | 42건·7.42분 | 71.9% 감소 |
| 문자 재안내 요청 | 0회 | 20회 | 기능 사용 확인 |
| 주문 / 음식 수량 | 58건 / 70개 | 49건 / 56개 | 음식 수량 20% 감소 |
| 결제 확인 금액 | 419,000원 | 336,000원 | 운영 규모 비교 |

인력과 숙련도는 비슷했고, 둘째 날에는 재료가 늦게 와 제작이 지연됐다. 그 조건에서도 기록상 완료 처리시간은 짧아졌다. 음식 1개 주문과 공통 접수 시간대에서도 같은 방향이었고, 15초 미만 기록 2건을 제외해도 평균 감소율은 약 69.4%였다.

다만 둘째 날 음식 수량은 20% 적었다. 재료 지연의 정확한 구간과 완료 버튼을 누르는 기준도 동일하게 측정하지 못했다. 따라서 71%는 **개선을 진행한 이틀의 기록 차이**다. UI 입력시간이나 순수 조리시간을 71% 줄였다는 뜻으로 쓰지 않았다. 15분·30분은 사후 분석 기준이고, 재안내 20회는 요청 수다.

이틀의 주문이 같은 대기열과 작업 환경을 공유하므로 독립표본 검정만으로 개선의 인과 효과를 확정하기도 어렵다. [통계 분석](statistical-review.md)에 표본·계산식·검정 가정과 [재현 코드](../scripts/analyze-operation-days.mjs)를 연결했다.

전체 실적 109건·128개·766,000원은 서버 기록 107건·126개·755,000원에 별도 확인한 예약 수령 2건·2개·11,000원을 더한 값이다. 예약 중복을 제외한 [집계 근거](operations-record.md#운영-결과와-집계-경계)는 따로 남겼다. 비용·순이익은 계산하지 않았다.

## 기술적으로 맡은 범위

| 영역 | 구현 |
| --- | --- |
| 고객 화면 | 주문 단계·입력 검증·필수 동의·입금 안내·제출 저널과 응답 유실 복구 |
| 관리자 화면 | 인증, 주문 카드·상세·상태 변경, 날짜별 이력·검색, 연락처·문자 재발송·보관 |
| 서버·DB | 금액 계산, SQLite 영구 저장·트랜잭션, 버전 검사, 요청 키·예약 ID 중복 방지 |
| 보안·연동 | 관리자 세션·Origin 검사, 전화번호 AES-256-GCM, Solapi 발송·전달 조회, 외부 예약 검증 |
| 예측 | 최근성 가중 비음수 회귀, 학습 갱신, 순차 검증·실제 예측 오차 계산 |
| 배포·검증 | Railway 단일 서버·영구 볼륨, 빌드·자동 테스트, 운영 상태·수치 분석 |

순차 검증 20건에서 예측 평균 절대 오차는 3.5분으로, 최근 10건 평균 방식의 4.0분보다 낮았다. 실제 접수 당시 예측과 완료를 비교한 최근 20건의 오차는 3.6분이었다. 테스트는 모의 문자 전송과 로컬·임시 저장소로 실행했다.

## 운영 후 정리와 다음 과제

행사 뒤에는 실제 흐름에 남아 있던 미사용 UI를 삭제하고, 판매 가능 여부 조회와 관리자 전체 조회를 분리했다. 보드에서 과거 이력을 매번 받지 않도록 바꾸고, 주문 응답의 고정 800ms 대기를 제거했다. 예약 수령코드도 6자리로 통일했다. 이 변경은 소스와 로컬 검증까지 마쳤고 아직 운영 서버에는 재배포하지 않았다.

운영하며 가장 크게 느낀 건 접수 화면뿐 아니라 재연락과 픽업, 처리 종료까지 설계해야 한다는 점이었다. 다음에는 준비 완료와 실제 전달 시각을 분리하고, 기기별 충돌과 접수 단계별 시간을 기록하려고 한다. 그래야 어떤 개선이 어디에 영향을 줬는지 더 정확히 비교할 수 있다.
