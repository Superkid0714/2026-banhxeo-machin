# 운영하며 바꾼 것

태블릿 2대로 축제 부스 주문 서비스를 운영했다. 만들 때 예상했던 흐름과 현장에서 필요한 흐름은 달랐다. 고객이 주문을 끝낸 뒤에도 화면에 머물렀고, 픽업 문자를 보냈는데도 다시 연락해야 하는 경우가 있었다. 이 문서는 그때 바꾼 화면과 기능, 운영 후 코드를 살펴보며 정리한 내용을 담았다.

## 운영 경험의 흐름

| 업무 | 겪은 문제·필요 | 바꾼 내용 |
| --- | --- | --- |
| 고객 접수 | 이용 방법·추가 확인·완료 화면에서 조작이 이어짐 | 불필요한 단계를 없애고 성공 후 홈으로 복귀 |
| 개인정보·입금 | 동의와 계좌 확인은 각각 필요 | 별도 화면 유지 |
| 고객 재연락 | 첫 문자 후 바로 찾아오지 않음 | 완료 단계에서도 픽업 재발송 |
| 주문 대조 | 직원에게 전체 연락처가 필요 | 인증된 관리자 번호 조회·검색 |
| 대기 안내 | 지금 주문하면 얼마나 걸리는지 질문 | 대기량·과거 기록으로 예측, 한 줄 표시 |
| 태블릿 2대 | 한쪽에서 바뀐 상태가 다른 화면에 늦게 보일 수 있음 | 서버 버전 검사·중복 방지·최신 조회 |

기기별 담당 배치와 개별 충돌 시각·버튼은 기록으로 남기지 못했다. 아래 동시 처리 예시는 코드의 동작을 설명한 것이다.

## 운영 중 UI 개선의 분석

처음에는 이용 방법 선택, 최종 확인, 제출 후 완료 화면이 있었다. 장사를 해보니 추가 정보를 받지 않는 단계가 접수를 길게 만들었다. 선택·추가 확인·완료 화면을 없애고 접수 성공 후 처음 화면으로 돌아가도록 바꿨다. 다음 고객을 받기 위해 직원이 화면을 정리할 필요가 없게 한 것이다.

개인정보 동의와 입금 계좌 확인은 합치지 않았다. 확인 목적이 다르고 둘 다 필요한 단계였다. 최종 흐름은 **상품·수량 → 전화번호 → 개인정보 동의 → 입금 안내·접수 → 홈**으로 정리했다. 제출 실패 때는 입력과 요청 키를 보존해 재시도하도록 했다.

관리자 대기시간 표시도 바꿨다. 처음에는 넓은 시간 범위, 학습 건수와 오차, 주문별 시간 초과 안내를 보여줬다. 바쁜 직원에게는 모델 설명보다 고객에게 말할 시간이 먼저였다. 화면을 **“지금 주문하면 약 ○분”** 한 줄로 줄이고 진단 정보는 서버에 남겼다.

UI 입력을 시작한 시각은 수집하지 않아 화면 변경만의 접수시간 단축률은 알 수 없다. 뒤에서 비교하는 지표는 서버 접수 이후 완료 처리까지의 시간이다.

## 운영 중 시스템 개선의 분석

### 재발송과 연락처 조회

문자를 보냈다는 사실만으로 고객이 찾아온 것은 아니었다. 이미 완료 단계로 옮긴 주문도 다시 픽업 안내를 보낼 수 있게 했다. 발송 중 재요청을 막고, 문자 서비스의 접수·전달·실패·불명 상태를 나눠 표시했다. 늦은 응답은 lease와 전달 ID를 검사해 반영한다.

직원이 직접 연락하거나 주문을 대조할 수 있도록 관리자 카드·상세·전체 이력에 전체 전화번호와 검색을 넣었다. 원문 번호는 서버에서 암호화하고 관리자 인증 뒤에만 조회한다. 고객 응답은 마스킹을 유지했다. 전화번호가 없는 예약은 미등록으로 표시한다.

재발송은 둘째 날 20회 요청됐다. 실제로 쓰인 기능이지만 전달 성공 20건이나 고객 방문 20명을 의미하지는 않는다.

### 상태·문자·보관

직원이 처리하는 순서에 맞춰 **결제확인 → 조리중 → 수령완료**로 단순화했다. 결제 확인 때 결제 안내, 수령완료 변경 때 픽업 안내를 요청한다. 결제 문자가 진행 중이면 그 결과 처리 뒤 픽업 안내를 이어 보낸다.

처리가 끝난 카드는 이력으로 보관해 보드에서 뺀다. 보관은 주문과 이력을 남기지만 취소·영구 삭제는 집계와 조회에도 영향을 준다. 특히 수령완료는 픽업 안내 시점으로도 사용했으므로 실제 고객 전달 시각과 같다고 보기는 어렵다.

### 대기시간 예측

대기시간 질문에 답할 기준이 필요했다. 접수부터 첫 준비·완료 처리까지 걸린 시간에 앞선 음식 수량과 새 주문 수량을 반영하는 최근성 가중 회귀를 넣었다. 최신 최대 80건을 쓰고 반감기는 120분이다. 새 접수는 대기량에 반영하고 완료 기록이 바뀌면 재학습한다.

접수 당시 예측을 저장해 실제 기록과 비교한다. 최근 20건의 운영 평균 절대 오차는 3.6분이었다. 입금·기록·고객 방문 지연이 섞일 수 있어 준비 완료와 실제 전달 시각을 따로 기록하는 것이 다음 과제다. [모델 구조](technical-reference.md#대기시간-모델과-한계)와 [검증 이력](operations-record.md#대기시간-모델의-검증-기록)을 연결했다.

## 태블릿 2대 운영과 동시 처리 충돌 대응

두 태블릿은 같은 서버를 사용하지만 화면과 브라우저 저장소는 각각 따로다. 관리자 화면은 5초 간격으로 갱신된다. 화면의 버튼이 활성화돼 있어도 다른 기기에서 그 주문을 먼저 처리했을 수 있다.

가령 A와 B가 같은 주문의 버전 3을 보고 있다고 하자. A가 결제를 확인하면 서버 버전이 올라간다. B가 갱신 전에 같은 버튼을 누르면 서버는 버전 3의 요청을 거부한다. B에는 이미 처리된 주문이라는 안내가 나오고 최신 상태를 다시 조회한다. 완전히 동시에 누르지 않아도 발생하는 상황이다.

| 상황 | 현재 처리 |
| --- | --- |
| 오래된 주문 변경 | HTTP 409 `ALREADY_PROCESSED`, 안내 후 재조회 |
| 오래된 판매·재고 설정 변경 | HTTP 409 `SETTINGS_CHANGED`, 최신 설정 확인 |
| 신규 주문 저장 | SQLite `BEGIN IMMEDIATE`에서 주문·번호·요청 키·재고 갱신 |
| 같은 요청 재시도 | 같은 키·본문이면 기존 주문 반환, 내용이 다르면 거부 |
| 같은 예약 재접수 | 예약 ID 키로 기존 주문 반환, 삭제 표식도 유지 |
| 문자 재요청 | pending·sending·submitted 상태에서 차단, 작업 lease 검사 |
| 오래된 조회 응답 | 화면 요청 순번으로 최신 조회만 반영 |
| 연결 실패 | 상태 변경 제한, 연결 복구 후 최신 데이터 조회 |

충돌 안내를 받으면 같은 버튼을 반복해서 누르기보다 갱신된 상태와 처리 이력을 먼저 본다. 제출 결과가 불명확할 때도 같은 요청 키·예약 코드로 기존 결과를 확인한다. 이 절차는 현재 구현에 따른 대응이며 당시 직원의 모든 행동을 복원한 기록은 아니다.

화면 안의 중복 클릭 잠금만으로 다른 기기까지 잠글 수는 없다. 같은 고객이 두 기기에서 서로 다른 새 요청 키로 제출하면 별도 주문이 된다. 또 관리자 계정 수준의 이력은 있지만 기기별 충돌 횟수·담당자·오류를 따로 기록하는 장부는 없다. 실제 충돌 감소율을 내려면 이런 기록이 더 필요하다.

중복 방지·복구·트랜잭션은 기존 기반 기능이다. 모든 보호 장치를 특정 충돌 사건 이후 새로 만들었다고 기록하지는 않았다. [구현과 테스트](engineering-decisions.md#반드시-유지하려는-조건과-테스트-연결)에 각 보호 범위를 정리했다.

## 운영 이후 점검으로 발견한 개선

행사를 마친 뒤 실제 사용한 흐름에 맞춰 코드를 다시 살폈다.

| 남아 있던 문제 | 정리한 내용 |
| --- | --- |
| 없앤 화면의 컴포넌트·타입·프레임이 남음 | `NotificationChoice` 삭제, 단계 결정 함수를 분리하고 이전 링크 호환 유지 |
| 판매 상태 조회가 관리자 전체 처리를 호출 | `availability()`로 분리해 불필요한 복호화·예측 호출 제거 |
| 보드에서 과거 전체 이력을 반복 전송 | `history=exclude` 조회, 관리자 매핑 재사용 |
| 저장 후 고정 800ms 대기 | 지연 제거, 제출 복구·중복 검증 유지 |
| 예약 코드 길이가 계층별로 다름 | 6자리 숫자로 통일, 잘못된 입력의 외부 요청 차단 |
| 예약 서버 주소가 코드에 고정 | 서버 전용 HTTPS 환경 설정 추가 |

이 변경은 코드와 로컬 검증까지 끝났고 운영 서버에는 아직 재배포하지 않았다. 전체 JSON 읽기·모델 계산은 여전히 남아 있다. 조회 최적화가 실제 응답시간을 얼마나 줄였는지는 다음 배포에서 측정해야 한다.

## 확인된 결과와 다음 운영의 측정

이틀의 기록 58건·49건을 비교했을 때 접수→완료 처리 평균은 **26.92분에서 7.92분으로 70.6% 감소**했다. 중앙값은 72.4%, 90백분위수는 60.5% 낮아졌다. 30분 초과 주문 비율은 **44.8%에서 2.0%로 42.8%p 감소**했고, 음식 1개 주문 평균도 71.9% 줄었다.

인력·숙련도는 비슷했고 둘째 날에는 재료 배송 지연이 있었다. 반면 음식 수량은 20% 적었다. 완료 버튼의 기준과 배송 지연 구간까지 통제한 실험은 아니므로, 수치는 개선을 진행한 이틀의 관측 차이로 남겼다. 15분·30분은 사후 탐색 기준이다. [전체 수치와 산식](operations-record.md#성과-지표-전체와-단위), [통계 분석](statistical-review.md)을 참고한다.

다음에는 접수 시작·저장·준비 완료·실제 전달을 따로 기록하려 한다. 기기별 충돌, 재안내 뒤 픽업까지의 지연, 예측 오차 분포도 함께 남기면 기능별 효과를 더 잘 볼 수 있다. UI 단계 수보다 중요한 건 고객 접수부터 재연락·전달·처리 종료까지 실제 업무가 이어지게 만드는 일이었다.
