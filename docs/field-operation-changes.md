# 현장 운영을 바탕으로 한 주문 시스템 개선

이 문서는 실제 부스 운영 중 사용자와 관리자가 겪은 문제, 변경 이유와 최종 동작을 기록한다. 처리 속도 개선을 수치로 측정한 실험 결과는 아니며, 현장 피드백에 따라 개선한 사항이다.

## 고객 주문 화면의 병목

운영 중 주문 화면에 불필요한 선택과 확인 단계가 남아 있어 고객이 입력을 마친 뒤에도 화면을 계속 조작해야 했다. 공유 주문 기기에서 이런 단계가 반복되면 다음 고객의 접수가 늦어질 수 있었다.

- 이용 방법 선택 화면을 제거하고 상품·수량 확인 뒤 전화번호 입력으로 연결했다.
- 별도 최종 확인 단계와 제출 직후의 주문 접수 완료 화면을 제거했다. 주문 제출에 성공하면 입력 상태를 정리하고 처음 화면으로 돌아가 다음 고객을 받을 수 있도록 했다.
- 개인정보 동의와 입금 계좌 확인은 서로 다른 목적이므로 각각의 화면으로 유지했다. 단계 수를 줄이더라도 개인정보 동의를 입금 안내에 합치지 않았다.
- 입금 안내에는 주문 수량, 금액, 계좌와 QR을 모아두고 그 화면에서 접수하도록 했다. 웹 접수와 실제 입금 확인은 구분하며, 직원이 입금을 확인해야 조리중으로 전환된다.
- 제출 실패 시 재시도를 유지한다. 고객의 기존 주문 조회 화면은 별도로 남겨 주문 상태를 확인할 수 있게 했다.

최종 현장 주문 흐름은 **상품·수량 → 전화번호 → 개인정보 동의 → 입금 안내·주문 제출 → 처음 화면**이다.

## 관리자 화면에서 실제로 필요했던 기능

문자를 한 번 보냈더라도 고객이 바로 찾아오지 않는 경우가 있었다. 따라서 수령완료로 옮긴 주문에서도 픽업 안내를 다시 보낼 수 있어야 했다. 여기서 현재 운영의 수령완료 처리는 픽업 문자 발송 시점으로도 쓰이므로, 실제 전달 및 처리 종료와 혼동하지 않도록 주의가 필요하다.

- 주문 카드와 상세에서 문자 재발송을 지원했다. 수령완료 주문에서는 픽업 안내를 다시 요청한다.
- 문자 발송이 대기·진행·접수 상태이면 재요청을 차단해 중복 발송을 줄인다. 요청 접수와 실제 발송 완료를 구분하고 실패·결과 불명 상태를 확인할 수 있도록 했다.
- 관리자가 고객에게 연락하고 주문을 대조할 수 있도록 인증된 관리자 화면에 전체 전화번호를 표시했다. 카드, 상세, 전체 주문 이력에서 확인하고 하이픈이나 공백이 있어도 검색할 수 있다. 전화번호 없는 사전예약은 미등록으로 표시한다.
- 관리자 기본 흐름을 **결제확인 → 조리중 → 수령완료**로 단순화했다. 결제 확인 시 결제 안내, 수령완료 변경 시 픽업 안내 문자를 요청한다. 앞선 결제 문자가 처리 중이면 이후 픽업 안내를 이어서 처리한다.
- 실제 처리가 끝난 주문은 **처리 완료·내역으로 이동**으로 대시보드에서 제외하고 이력에 보관한다. 취소는 삭제 및 집계 제외를 수행하므로 확인창에서 그 결과를 명시한다.

## 대기시간 질문에 답하기 위한 예측

관리자가 새로 주문하는 고객에게 어느 정도 기다리는지 설명할 수 있도록, 주문 접수부터 첫 조리 완료 또는 수령완료 처리까지의 시간 기록을 사용했다. 별도 외부 AI 서비스에 고객 정보를 보내지 않는다.

| 항목 | 구현 |
| --- | --- |
| 모델 | 비음수 계수와 정규화를 사용하는 최근성 가중 회귀 |
| 입력 | 기본 소요시간, 접수 당시 앞선 미완료 음식 수량, 새 주문 수량 |
| 학습 기록 | 유효한 완료 기록 중 최신 최대 80건 |
| 최근성 | 반감기 120분. 최신 기록에 더 높은 가중치를 부여 |
| 갱신 | 새 접수는 대기 수량에 반영하고, 유효한 완료 기록이 바뀌면 재학습. 관리자 조회는 5초 간격 |
| 신규 주문 안내 | 음식 1개를 지금 주문하는 경우의 대표 예상 시간 |
| 표시 | “지금 주문하면 약 10분” 한 문장. 5분 단위 반올림, 5분 이하는 1분 단위 |
| 데이터 유지 | 저장된 주문 기록으로 모델을 재구성하므로 재시작 후에도 기록을 반영 |

처음에는 예측 범위, 학습 건수, 오차, 갱신 주기와 주문별 시간 초과 안내를 노출했다. 현장 관리자가 필요한 것은 신규 주문의 간단한 시간 안내였으므로 해당 설명들을 화면에서 제거했다. 내부 예측 범위와 검증 지표는 서버에 유지한다. 표시를 한 숫자로 바꾼 것 자체가 모델 정확도를 높인 것은 아니다.

개선 당시 과거 순차 검증 20건의 평균 절대 오차는 약 4.9분이었고, 같은 검증 대상에 대한 최근 10건 단순 평균 방식은 약 7.4분이었다. 이 수치는 특정 시점의 참고 결과이며, 확률이나 보장 범위가 아니다. 당시 신규 주문에 저장한 예측과 실제 완료를 비교하는 운영 검증은 아직 완료 표본이 없었다. 앞으로 접수 당시 예측을 내부 저장하고 완료 후 실제 시간과 비교해 최근 20건의 운영 오차를 집계한다.

입금 확인 지연이 학습 시간에 포함된다. 완료 버튼을 실제 수령 때 누르면 고객 방문 지연도 포함되므로 순수 조리시간과는 다를 수 있다. 음식 준비 완료 시점에 일관되게 기록해야 “접수부터 준비까지”의 예측에 가까워진다. 화면의 예상 시간은 현장 안내를 위한 참고값으로 사용한다.

## 민감한 정보와 배포 설정

- 실제 고객 전화번호, 관리자 자격 증명, API 키, 암호화 키, 주문 DB, 로컬 검증 결과·화면은 커밋하지 않는다. 테스트는 가상 번호와 모의 문자 전송을 사용한다.
- 전체 전화번호는 인증된 관리자 조회에만 제공한다. 고객 API에는 마스킹된 연락처를 유지하고, 저장 전화번호는 AES-256-GCM으로 암호화한다.
- 계좌번호와 예금주는 소스에 직접 넣지 않고 `VITE_PAYMENT_BANK`, `VITE_PAYMENT_HOLDER`, `VITE_PAYMENT_ACCOUNT` 빌드 환경 변수로 관리한다. 로컬 값은 Git에서 제외된 `.env.production.local` 등에 보관하고, 공유 예시는 빈 값만 제공한다.
- 위 `VITE_*` 값은 고객의 입금 안내 화면에 공개되는 값이다. API 키나 비밀번호를 이 변수에 넣으면 안 된다.
- 계좌별 QR 이미지 `public/assets/payment-qr.jpg`는 GitHub에서 제외한다. 로컬 Railway CLI 배포에서는 `.railwayignore`를 사용해 이 이미지를 포함하고 비밀 환경 파일·DB·검증 자료는 제외한다. GitHub checkout만으로 배포하는 경우에는 빌드 환경 변수를 설정하고 QR 이미지를 별도로 공급해야 한다.

## 검증과 남은 확인

고객 흐름 및 관리자 변경은 타입 검사와 프로덕션 빌드로 확인한다. 주문 상태 전이, 문자 재발송·경합, 관리자 인증 및 전화번호 공개 범위, 사전예약, 대기시간 모델은 관련 자동 테스트로 검증한다. 운영 서버에서는 실제 고객 주문을 임의로 변경하지 않고 화면 번들, 인증과 API 및 관리자 표시를 확인했다.

이번 개선 전후의 고객당 접수 시간과 실제 대기열 감소는 별도로 측정하지 않았다. 다음 운영에서는 접수 흐름의 병목이 줄었는지, 재발송·연락처 조회가 도움이 되는지, 실제 준비 시점과 예상 시간의 차이가 어떤지 확인할 필요가 있다.
