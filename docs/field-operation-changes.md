# 실제 운영 경험에 따른 UI·시스템 개선 분석

이 문서는 실제 부스 운영 중 사용자와 관리자가 겪은 문제, 변경 이유와 최종 동작을 기록한다. 처리 속도 개선을 수치로 측정한 실험 결과는 아니며, 현장 피드백에 따라 개선한 사항이다.

운영 중 피드백을 받아 적용한 개선과, 운영을 마친 뒤 코드를 점검해 발견하고 구현한 개선을 함께 기록한다. 후자는 2026-11-26에 소스에 반영한 작업이며 현장 운영 중 적용한 변경과 구분한다. 전체 실적·최신 예측 지표는 [운영 총정리](operations-record.md)에, 구현·배포 여부는 [기술 종합](technical-reference.md)과 [배포 기록](deployment-runbook.md)에 정리했다. 아래 초기 58건·오차 4.9분은 당시 수치다.

## 운영 경험의 흐름

태블릿 2대를 사용한 축제 부스에서 고객 접수, 직원의 입금 확인·조리·픽업 안내, 처리 완료와 정산을 지원했다. 기기별 담당 역할은 확정 기록이 없으므로 임의로 배정하지 않는다. 다음은 개별 사건의 정확한 시간순서가 아니라 업무 흐름에 따른 회고 순서다.

| 업무 장면 | 경험 또는 확인된 요구 | 판단·대응 | 상세 기록 |
| --- | --- | --- | --- |
| 고객이 주문 기기를 사용 | 운영 중 접수 병목, 불필요한 선택·완료 단계 | 다음 고객의 접수를 막는 조작을 줄이되 동의·입금 확인은 분리 유지 | [UI 개선](#운영-중-ui-개선의-분석) |
| 직원이 고객에게 재연락 | 첫 문자 후 바로 오지 않는 고객, 전체 연락처 필요 | 재발송과 관리자 번호 조회를 서버 보호 조건과 함께 제공 | [시스템 개선](#운영-중-시스템-개선의-분석) |
| 직원이 진행 주문을 정리 | 현장 상태 흐름과 화면의 조작·보관 업무를 맞출 필요 | 상태·문자 연계와 보드/이력 역할 정리 | [시스템 개선](#운영-중-시스템-개선의-분석) |
| 새 고객이 대기시간을 질문 | 현재 주문 시 걸릴 시간을 직관적으로 안내할 필요 | 과거 기록·현재 대기량으로 예측, 관리자 표시는 한 줄로 정리 | [UI·시스템 분석](#운영-중-ui-개선의-분석) |
| 두 기기에서 같은 서비스를 사용 | 태블릿 2대 운영, 충돌 상황 언급 | 버전 검사·트랜잭션·중복 방지·재조회로 처리. 구체 당시 행동은 미확인 | [동시 처리 대응](#태블릿-2대-운영과-동시-처리-충돌-대응) |
| 행사를 마치고 코드를 재점검 | 사용하지 않는 UI와 조회·지연·입력 계약의 개선점 발견 | 소스 정리·로컬 검증, 운영 배포와 효과 확인은 별도 | [운영 이후 개선](#운영-이후-점검으로-발견한-개선) |

각 경험은 **환경·문제 → 원인에 대한 판단 → UI·서버 조치 → 확인된 동작 → 남은 검증**으로 읽는다. 운영자의 직접 설명, 코드로 확인한 사실, 설명용 시나리오, 향후 제안을 섞어 성과로 표현하지 않는다.

## 분석의 기준과 근거

사용자는 실제 장사 중 주문 단계에서 병목을 겪어 UI를 바꿨고, 관리자 화면을 사용하면서 재발송과 전체 전화번호가 필요해졌다고 설명했다. 따라서 이 변경은 디자인 취향만으로 바꾼 것이 아니라 현장의 고객 접수·연락·픽업 업무에 맞춘 개선으로 기록한다.

근거는 운영자의 피드백, 요청에 따른 변경 이력, 실제 구현과 배포 확인이다. 개별 고객의 관찰 시간·클릭 로그·대기열 길이·전후 처리시간은 수집하지 않았으므로 이 문서는 정량적인 사용자 실험 결과가 아니다. 반복 조회의 내부 비용 등은 운영 후 코드 점검에서 발견한 구조이며, 당시 장애의 원인으로 실측 확정한 것은 아니다.

| 구분 | 무엇을 근거로 개선했는가 | 대표 변경 | 효과의 확인 범위 |
| --- | --- | --- | --- |
| 운영 중 UI 개선 | 접수 병목, 단계 불필요, 관리자 정보 과다라는 피드백 | 선택·완료 화면 제거, 동의·계좌 분리, 예상 시간 한 줄 | 화면·동작과 배포 확인. 처리시간 감소율은 미측정 |
| 운영 중 시스템 개선 | 한 번에 찾아오지 않는 고객, 연락·주문 대조, 대기시간 질문 | 재발송·전체 번호·상태 단순화·보관·예측 | 기능·보호 조건·집계 확인. 미수령 감소율·인력 절감은 미측정 |
| 운영 이후 개선 | 실제 사용한 흐름을 기준으로 소스와 API 경로 재점검 | 미사용 UI 삭제, 조회 분리, 응답 지연 제거, 예약 검증 통일 | 소스 구현 및 로컬 검증. 운영 재배포·현장 효과 검증은 아직 없음 |

## 운영 중 UI 개선의 분석

| 실제 문제·요청 | 원인에 대한 분석 | 변경 내용 | 개선된 동작과 남은 확인 |
| --- | --- | --- | --- |
| 장사 중 접수 단계에서 병목 발생. 이용 방법과 step3·완료 화면이 필요 없다는 요청 | 공유 주문 기기에서는 제출 이후의 화면도 한 고객이 기기를 점유하는 시간에 포함됨. 거래에 추가 정보가 필요 없는 확인 단계가 남아 있었음 | 이용 방법·추가 최종 확인·제출 직후 완료 화면 제거, 성공 후 홈 복귀 | 다음 고객이 접수를 시작할 준비 상태로 자동 복귀. 실제 접수시간 단축 폭은 미측정 |
| 개인정보 화면과 계좌 화면은 구분해야 한다는 요청 | 단계 축소만 우선하면 동의와 입금 확인이라는 서로 다른 행동을 한 번에 처리하게 됨 | 전화번호·개인정보 동의·입금 안내의 목적을 구분하고 별도 화면 유지 | 필수 확인을 유지하면서 불필요한 화면만 제거. 동의 이해도·입금 실수율은 미측정 |
| 대기 범위가 넓고 학습 건수·오차·시간 초과 등 설명이 과다함 | 관리자의 당면 업무는 모델 상태 해석보다 지금 접수할 고객에게 시간을 안내하는 것 | 새 음식 1개 기준 “지금 주문하면 약 ○분” 한 줄 표시 | 안내해야 할 값을 바로 찾을 수 있는 구성. 화면 단순화 자체가 예측 오차를 줄인 것은 아님 |

접수 UX의 목표는 화면 수 자체의 최소화가 아니라 **고객이 필요한 입력과 확인을 마치면 다음 고객에게 기기를 넘길 수 있게 하는 것**이었다. 개인정보 동의·계좌 확인은 유지하고 중복 선택·확인·완료 조작을 줄였다는 점이 핵심이다.

## 운영 중 시스템 개선의 분석

| 운영에서 드러난 필요 | 시스템 관점의 분석 | 반영한 기능·보호 조건 | 확인된 범위와 한계 |
| --- | --- | --- | --- |
| 안내 문자를 받고도 한 번에 찾아오지 않는 고객 | 발송 성공과 실제 고객 방문은 다른 사건. 한 번 보낸 뒤에도 직원이 다시 연락하는 후속 업무가 필요함 | 수령완료 카드·상세의 픽업 재발송, 진행 중 중복 요청 차단, 발송 결과 구분 | 재안내 경로가 생김. 고객 방문률 개선은 측정하지 않음 |
| 관리자에게 전체 전화번호가 필요함 | 고객용 마스킹 정보와 현장 직원의 연락·대조에 필요한 정보의 범위가 달랐음 | 인증된 관리자 조회에서 전체 번호·검색 제공, 고객 응답은 마스킹·저장 시 암호화 유지 | 관리자가 시스템 안에서 연락처 확인 가능. 실제 연락 횟수·소요시간은 미측정 |
| 바쁜 현장에서 상태·문자·처리 종료를 관리해야 함 | 세분화한 상태와 실제 직원의 처리 단위가 다르고, 완료 카드 정리가 필요했음 | 결제확인 → 조리중 → 수령완료로 단순화, 상태에 맞는 문자 예약, 보관 기능 | 조작 흐름과 보드·이력 역할을 정리. 픽업 안내와 실제 전달 시점의 명칭 혼재는 남음 |
| 예상 대기시간을 질문받음 | 과거 평균만으로는 현재 앞에 밀린 음식 수량의 영향을 표현하기 어려움 | 과거 완료 기록·접수 당시 대기량·수량의 최근성 가중 회귀, 새 접수 반영·완료 후 재학습·오차 기록 | 자동으로 갱신되는 안내 기준 마련. 학습 시각·입금·고객 방문 지연 영향을 계속 점검해야 함 |

재발송은 버튼만 추가한 변경이 아니다. 어느 단계에서 어떤 안내를 다시 보내는지, 처리 중 요청을 허용할지, 외부 서비스 접수와 전달 결과를 어떻게 구분할지 함께 다뤘다. 전체 번호 표시 역시 인증된 관리자 응답과 고객 응답의 경계를 유지하는 서버 변경을 동반했다. 즉 운영 중 UI 개선과 시스템 개선은 같은 업무 문제를 화면과 서버 양쪽에서 해결한 것이다.

중복 접수 방지·제출 복구·DB 트랜잭션·암호화는 이 개선을 받치는 기존 기반이다. 운영자는 태블릿 2대 운영과 충돌 상황을 언급했다. 다만 개별 주문의 중복 생성이나 개인정보 유출 사고를 확인한 것은 아니며, 모든 보호 장치를 그 사건 이후 새로 도입했다고 서술하지 않는다.

## 태블릿 2대 운영과 동시 처리 충돌 대응

### 실제 운영 환경과 기록 범위

운영자는 **태블릿 2대로 서비스를 운영했다**고 확인했다. 여기서 말하는 두 기기는 예약 서비스와 주문 서비스라는 두 백엔드를 뜻하지 않는다. 두 태블릿이 같은 주문 서비스의 서버·DB를 이용할 때 각 화면에 보이는 상태와 실제 서버 상태가 다를 수 있다는 동시 처리 문제를 다룬다.

태블릿별 고객용·관리자용 역할 배치, 충돌한 주문·시각·버튼, 당시 오류 코드와 발생 횟수는 별도로 확인되지 않았다. 따라서 아래의 A/B 예시는 **현재 코드가 처리하는 동작을 설명하는 예시**이며 실제 사건의 상세 로그를 재구성한 것은 아니다. 이미 존재하는 보호 기능의 도입 시점을 해당 경험 이후로 바꾸어 기록하지 않는다.

### 왜 충돌할 수 있는가

각 태블릿은 독립된 화면·브라우저 저장소를 사용한다. 관리자 화면은 5초마다 서버를 조회하므로 다른 기기의 변경이 그 사이 즉시 표시되는 구조는 아니다. 한쪽 화면의 버튼이 활성 상태라고 해서 그 주문이 아직 같은 상태라는 뜻은 아니다. 버튼의 로컬 잠금은 같은 화면의 연속 클릭을 막지만 다른 태블릿의 요청까지 잠그지 못한다.

예를 들어 두 관리자 화면이 같은 주문의 버전 3을 보고 있다고 가정한다. A에서 결제 확인이 성공하면 서버는 상태를 바꾸고 버전을 올린다. B가 이전 버전 3으로 변경을 요청하면 서버는 이를 거부한다. 이때 B의 화면에는 잠시 예전 상태가 보일 수 있지만, 뒤늦은 요청이 A의 성공한 처리를 덮어쓰지는 않는다.

사용자의 행동으로 풀면 **A에서 결제 확인 클릭 → B의 다음 조회 전에 B에서도 같은 주문의 결제 확인 클릭 → B에 이미 처리됐다는 안내 → 최신 상태 조회**다. 완전히 동시에 누르지 않아도 발생할 수 있다. 이 예시의 거부 응답은 이미 처리된 주문을 다시 변경하지 않도록 작동한 보호 결과이며, DB 충돌·주문 유실이 실제로 일어났다는 증거가 아니다. 다른 정상 주문을 두 기기에서 각각 접수하는 상황과도 구분한다.

### 현재 구현된 대응

| 동시 사용 상황 | 서버·화면의 대응 | 보호 범위 |
| --- | --- | --- |
| 두 관리자 화면에서 같은 주문을 변경 | 현재 `version` 비교 후 오래된 요청은 HTTP 409 `ALREADY_PROCESSED`로 거부. 화면에 이미 처리된 주문 안내 후 다시 조회 | 먼저 성공한 변경을 뒤늦은 화면 상태로 덮어쓰지 않음 |
| 두 화면에서 판매·재고 설정을 변경 | 설정 버전 불일치 시 HTTP 409 `SETTINGS_CHANGED`, 최신 설정 재조회 안내 | 오래된 설정으로 다른 변경을 덮어쓰지 않음 |
| 서로 다른 신규 주문이 같은 시점에 접수 | 서버의 SQLite `BEGIN IMMEDIATE` 트랜잭션에서 요청 키·주문번호·주문·재고를 함께 변경 | 현재 단일 서버·DB에서 생성 정합성 유지 |
| 같은 현장 주문 요청을 재시도 | 같은 requestId·본문이면 기존 주문 반환, 같은 키의 다른 본문은 충돌 거부 | 같은 제출 요청의 재시도를 중복 생성하지 않음 |
| 같은 예약을 두 기기에서 접수 | 예약 ID 기반 키를 같은 트랜잭션에서 확인해 기존 주문 반환. 삭제 후에도 재생성 차단 | 기기별 다른 요청이어도 같은 예약 ID는 중복 접수 방지 |
| 두 화면에서 문자 재발송 시도 | 주문 버전 검사와 pending·sending·submitted 상태의 재요청 차단, 발송 작업의 lease 검사 | 진행 중 문자 중복 요청·오래된 발송 결과 반영 방지. 통신사 전달의 정확히 한 번 보장은 아님 |
| 관리자 조회 응답이 순서와 다르게 도착 | 화면의 요청 순번을 검사해 더 오래된 요청의 응답을 무시 | 늦게 도착한 과거 조회로 새 화면을 덮어쓰는 문제 완화 |
| 네트워크 연결이 끊김 | 연결 실패를 표시하고 상태 변경을 막음. 조회 복구 시 최신 주문으로 갱신 | 확인되지 않은 화면 상태에서 계속 처리하는 위험 완화 |

이 대응은 서버를 최종 상태의 기준으로 두고 **버전 검사·트랜잭션·요청별 중복 방지·재조회**를 결합한 방식이다. 실시간 푸시 동기화나 두 태블릿 간 직접 데이터 동기화는 아니다. 11월의 보드 조회 최적화는 이후 소스 개선이며 이 동시성 보호가 그때 처음 구현됐다는 뜻은 아니다.

### 충돌 안내를 만났을 때의 운영 절차

1. 이미 처리됐다는 안내가 나오면 같은 동작을 반복하지 않고 자동 재조회된 최신 상태를 확인한다.
2. 다른 담당자가 먼저 처리했는지 주문의 상태·처리 이력·문자 상태를 확인한다. 오래된 화면만 보고 결제 확인이나 픽업 문자를 다시 요청하지 않는다.
3. 접수 결과가 불명확하면 같은 요청 키 또는 같은 예약 코드로 기존 결과를 확인한다. 새 키의 주문을 임의로 추가해 해결하지 않는다.
4. 연결 실패 중에는 추가 처리를 멈추고 복구 후 갱신된 화면을 기준으로 업무를 이어간다.

이는 현재 구현에 맞춘 대응 절차다. 당시 담당자들이 이 순서를 모두 수행했다는 별도 관찰 기록은 없으므로 과거의 실제 조치 이력으로 단정하지 않는다.

### 남은 한계와 다음 운영의 확인 항목

두 태블릿에서 같은 고객의 현장 주문을 **서로 다른 새 requestId**로 각각 만들면 별도 주문이다. 전화번호가 같다는 이유만으로 중복을 합치지 않으며, 같은 탭 저널도 다른 기기에 공유되지 않는다. 같은 요청 재시도와 같은 고객의 별도 제출은 구분해야 한다.

현재 이력의 actor는 관리자 계정 수준이며 충돌 요청별 기기 ID·담당자·화면 버전·발생 횟수를 기록하는 전용 장부는 없다. 그래서 충돌 방지 코드가 있다는 사실만으로 당시 충돌 원인이나 감소율을 입증할 수 없다. 기존 자동 테스트는 오래된 버전 거부, 동일 키 동시 생성, 예약 동시 접수 등을 검증하지만 실제 태블릿 2대·현장 무선망의 모든 동작을 재현한 시험은 아니다.

다음 운영에서는 두 기기의 역할과 충돌 시 담당자 확인 절차를 정하고, 개인정보를 제외한 기기 구분·요청 종류·서버/화면 버전·응답 코드를 남기는 방안을 검토한다. 필요하면 실시간 갱신이나 서버 측 작업 담당 표시를 검토하되, 현재 구현 완료로 기록하지 않는다.

## 운영 이후 점검으로 발견한 개선

운영을 마친 뒤 실제 사용한 고객·관리자 흐름을 기준으로 코드를 다시 확인했다. 2026-11-26 작업은 이 점검에서 발견한 개선을 구현한 것으로, 단순히 날짜를 붙인 리팩터링보다 **운영 후 회고에 따른 구조·응답·계약 개선**으로 설명한다.

| 사후 점검에서 발견한 사항 | 실제 운영 경험과의 연결 | 구현한 개선 | 검증·효과의 범위 |
| --- | --- | --- | --- |
| 화면에서는 알림 선택을 없앴지만 관련 컴포넌트·타입·프레임이 남음 | 현장에서 확정한 간소화 흐름과 유지보수 코드가 어긋남 | 미사용 `NotificationChoice` 등 삭제, `resolveCheckoutStep`으로 경로·복구 조건 분리, 이전 링크 호환 유지 | 코드와 실제 흐름을 일치시킴. 화면 축소는 앞선 운영 중 개선이며 이 삭제로 새로 달성한 것은 아님 |
| 판매 가능 여부만 조회해도 전체 관리자 snapshot을 계산 | 고객 진입마다 필요한 판매 상태와 관리자용 이력·번호·예측의 요구가 다름 | 설정 전용 `availability()`로 복호화·예측 호출 경로 분리 | 불필요한 작업을 코드 경로에서 제거. 실제 처리량 증가율은 미측정 |
| 보드 폴링 때 전체 과거 이력까지 내려받음 | 바쁜 현장에서는 현재 처리 주문 확인이 우선이고 전체 이력은 별도 조회 업무임 | `history=exclude`로 보드와 전체 이력 응답을 구분, 중복 관리자 매핑 재사용 | 불필요한 응답 데이터와 중복 매핑을 줄임. 전체 DB JSON 읽기·모델 계산은 남음 |
| 접수 저장 뒤 800ms 고정 대기가 남음 | 현장에서 접수 병목을 줄인 목표와 관계없는 대기 시간이 서버에 존재 | 고정 지연 제거, 요청 키·본문 검증·제출 복구 유지 | 인위적 대기 원인을 제거. 전체 응답시간·고객 대기시간이 동일 수치만큼 줄었다고 측정한 것은 아님 |
| 예약 수령코드 형식이 계층마다 다름 | 고객 입력을 예약 서비스와 같은 계약으로 검증해야 불필요한 실패를 줄일 수 있음 | 화면·프록시를 6자리 숫자로 통일, 잘못된 입력의 외부 호출 차단 | 형식 불일치 경로를 자동 테스트로 확인. 실제 예약 실패 감소율은 미측정 |
| 예약 서버 주소 변경이 코드에 의존 | 차기 운영·검증 환경에서 연계 주소를 관리할 필요 | 서버 전용 HTTPS endpoint 환경 설정 지원 | 운영·검증 설정을 분리할 기반. 키는 브라우저로 노출하지 않음 |

이 개선은 소스에 구현했고 로컬 빌드·자동 테스트로 검증했다. **운영 서버에는 아직 재배포하지 않았으므로 현장 적용 효과가 확인된 변경으로 쓰지 않는다.** 코드 반영과 배포 상태는 [배포 기록](deployment-runbook.md)에 남긴다.

## 경험에서 얻은 설계 기준

- 고객 화면은 접수 완료 뒤 다음 고객의 시작 상태까지 포함해 설계한다.
- 화면을 줄일 때 개인정보 동의·입금처럼 목적이 다른 필수 확인은 구분한다.
- 문자 전송·준비·방문·실제 전달을 서로 다른 사건으로 다루고 재연락 경로를 마련한다.
- 직원에게는 업무에 필요한 정보와 조작을 제공하되 고객 응답과 서버 비밀 정보의 경계는 유지한다.
- 현재 처리 보드, 과거 이력, 모델 진단은 사용 목적이 다르므로 조회와 표시를 목적에 맞춘다.
- 현장에서 필요성을 확인한 변경, 코드 점검으로 발견한 개선, 다음 운영에서 검증할 가설을 구분해 기록한다.

이 사례의 의미는 화면을 줄이거나 기능을 늘린 건수보다, **실제 접수·연락·안내·처리 종료 과정에서 확인한 문제를 요구사항으로 바꾸고 UI와 서버에 함께 반영한 것**에 있다. 다음 운영에서는 접수시간·재연락 횟수·픽업 지연·예측 오차를 수집해 지금의 정성적 개선 근거를 보완해야 한다.

## 확인된 결과와 다음 운영의 측정

이 문서의 결과는 동작 확인, 검증 결과, 기대 효과를 구분한다. 기능이 추가됐다는 사실을 곧바로 현장 처리량이나 고객 만족도 향상 수치로 바꾸지 않는다.

| 구분 | 현재 기록할 수 있는 결과 | 아직 입증하지 못한 효과 | 다음 운영에서 남길 자료 |
| --- | --- | --- | --- |
| 고객 접수 | 불필요한 단계 제거, 필수 동의·입금 확인 유지, 성공 후 홈 복귀 | 고객당 접수시간·기기 점유시간 감소율 | 접수 시작·제출·홈 복귀 시각, 단계별 이탈·재시도 건수 |
| 재안내·연락 | 픽업 재발송 경로, 진행 중 중복 요청 차단, 관리자 전체 번호 조회 | 미수령·문의·연락 업무 시간 감소 | 개인정보를 제외한 재안내 횟수와 준비·실제 전달 간 지연 |
| 관리자 업무 | 상태 흐름·문자 연계·보관과 이력 조회를 구현 | 직원 처리량·오조작 감소 | 상태별 처리 시각과 오류 종류, 보관·삭제 사유 구분 |
| 두 태블릿 동시 사용 | 서버 버전 검사·중복 방지·재조회 구현 및 관련 자동 테스트 | 실제 현장 충돌 빈도·감소율 | 기기 구분, 요청 종류·버전·응답 코드·발생 시각. 실제 전화번호는 제외 |
| 대기시간 안내 | 현재 대기량 반영·완료 후 재학습·원래 예측과 실제 완료 비교 | 모든 주문의 시간 보장, UI 단순화에 따른 정확도 향상 | 원래 안내값·준비 시각·실제 전달 시각, 큰 오차·지속적 과소예측 |
| 운영 후 개선 | 미사용 코드·불필요한 조회·고정 지연·입력 계약을 소스에서 정리 | 운영 응답시간·전송량·예약 실패율의 실제 개선 폭 | 다음 배포 전후 같은 조건의 측정 및 기능 확인 |

2026-11-26 확인한 전체 실적은 운영자 별도 확인분을 포함해 109건·128개·766,000원이다. 주문 서버 API 기록과 별도 확인분을 분리한 계산 근거는 [운영 기록](operations-record.md#운영-결과와-집계-경계)에 보관한다. 이 실적 전체를 특정 개선의 성과로 귀속하지 않는다.

초기 58건 학습 시 과거 검증 오차는 4.9분이었고, 11월 26일에는 학습 80건 기준 과거 검증 오차 3.5분, 접수 당시 예측과 실제 완료를 비교한 최근 20건의 운영 오차 3.6분을 확인했다. 표본 시점이 다르며 모델 개선의 인과 효과로 해석하지 않는다. 상세 지표는 [검증 기록](operations-record.md#대기시간-모델의-검증-기록)에 모았다.

기술 구현·민감 정보 경계는 [기술 종합](technical-reference.md), 계좌 빌드 변수·QR·배포 입력과 장애·백업 절차는 [배포 운영 절차](deployment-runbook.md)를 따른다. 같은 내용을 이 문서에 복제하지 않는다. 현재 코드의 빌드 및 자동 테스트 48건 통과는 앞선 11월 26일 검증 결과이며, 실제 태블릿 2대·무선망·고객의 전체 행동을 재현한 현장 시험과는 구분한다.
