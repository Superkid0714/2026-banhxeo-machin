# 이틀 운영 결과 분석

서버에 남은 완료 기록 107건을 운영이 끝난 뒤 비교했다. 평균·분포·장시간 처리 비율과 조건별 비교를 정리하고, 검정 결과를 해석할 때 필요한 가정을 적었다. 무작위 비교 실험은 아니므로 관측된 감소와 개선만의 인과 효과는 구별한다.

## 업무 가설과 통계 가설

운영 당시의 판단을 가설로 정리하면 다음과 같다.

> 불필요한 고객 조작과 관리자 업무의 마찰을 줄이면 주문 처리 흐름이 원활해지고 접수부터 완료 처리까지의 시간이 짧아질 것이다.

가설을 사전 등록하거나 71%라는 목표를 먼저 정해 둔 것은 아니다. UI 단계 축소·홈 복귀, 관리자 재발송·연락처 조회·상태 정리를 실행한 뒤 운영 기록으로 관측 차이를 평가했다. 개선별 정확한 적용 시각을 기록하지 않아 첫째 날 전체를 엄밀한 미처치군, 둘째 날 전체를 처치군이라고 지정하지 않는다.

독립표본 검정의 귀무가설은 두 집단의 평균이 같다는 `H0: μ1 = μ2`, 양측 대립가설은 `H1: μ1 ≠ μ2`다. 이는 “서비스 개선의 효과가 없다/있다”라는 인과 가설과 동일하지 않다. 결과를 본 후 진행한 분석이므로 단측 검정으로 유리한 p값을 선택하지 않는다.

## 지표와 관측 결과

각 주문 i의 소요시간은 `Ti = (첫 준비·수령완료 이력 시각 - createdAt) / 60초`로 정의한다. 이번 자료는 첫 대상 이벤트가 모두 `수령 완료`였으며 보관 시각 `finishedAt`을 사용하지 않는다. 한국 접수 날짜로 58건·49건을 구분하고 전부 사용했다. 삭제 주문과 시간 기록 없는 별도 예약 2건은 포함하지 않는다.

| 지표 | 첫째 날 10/6 | 둘째 날 10/7 |
| --- | ---: | ---: |
| 주문 수 | 58 | 49 |
| 음식 수량 | 70 | 56 |
| 평균 | 26.9191분 | 7.9182분 |
| 표본 표준편차 | 10.2308분 | 5.9445분 |
| 중앙값: nearest-rank | 29.0910분 | 8.0346분 |
| 90백분위수: nearest-rank | 38.9532분 | 15.3767분 |

`평균 차이 = 26.9190663793 - 7.9181523810 = 19.000914분`

`감소율 = 평균 차이 / 첫째 날 평균 × 100 = 70.585338% ≈ 71%`

표시용 반올림 전 원래 값으로 계산한다. 중앙값·90백분위수도 각각 약 72.4%·60.5% 감소했다. 평균만 보고 선택한 하나의 유리한 지표로 설명하지 않는다. [상세 집계 기준](operations-record.md#이틀-운영의-수치-비교)을 따른다.

## 민감도 분석과 조건별 기술 비교

### 장시간 완료 처리 비율

| 기준 | 첫째 날 | 둘째 날 | 비율의 절대 감소 |
| --- | --- | --- | --- |
| 15분 초과 | 49/58건·84.4828% | 6/49건·12.2449% | 72.2379%p |
| 30분 초과 | 26/58건·44.8276% | 1/49건·2.0408% | 42.7868%p |

각 비율은 `기준분보다 엄격히 큰 소요시간의 건수 / 유효한 완료 기록 수 × 100`이다. 15분·30분은 자료를 본 뒤 추가한 탐색 기준이며 사전 SLA나 사전 등록 평가 지표가 아니다. 비율 차이는 `%p`로 쓰고 상대 감소율과 혼용하지 않는다. 임계값을 여러 개 탐색해 유리한 p값을 고른 것이 아니며, 별도 유의성 검정은 추가하지 않았다.

| --- | --- | --- | --- |
| 모든 잔존 완료 기록 | 58건·26.92분 | 49건·7.92분 | 대표 감소율 약 70.6% |
| 15초~120분 기준 | 58건·26.92분 | 47건·8.25분 | 짧은 기록 2건을 빼도 약 69.4% 감소 |

음식 1개 주문의 평균 감소율은 71.9262%다. 개수별 구성을 일부 맞춘 기술 비교이지 주문량·대기열·날짜 조건을 모두 보정한 인과 효과가 아니다.

15초 미만 기록이 실제 시험 주문이라고 확인된 것은 아니므로 대표 비교에서는 제외하지 않았다. 음식 1개 비교도 15초 기준을 적용하지 않은 별도 보조 분석이다. 표본 조건을 섞어 기재하지 않는다.

## 독립 주문을 가정한 검정: 탐색 결과만 보고

Welch 통계량은 `t = (x̄1 - x̄2) / sqrt(s1²/n1 + s2²/n2)`다. 두 집단의 분산이 같다는 가정을 하지 않지만 **표본 독립성은 여전히 요구**한다. SciPy의 `ttest_ind(equal_var=False, alternative="two-sided")`와 95% 평균 차이 구간을 사용했다. [공식 검정·구간 정의](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.ttest_ind.html)

| 독립표본 가정을 둔 탐색값 | 결과 |
| --- | ---: |
| Welch t / 자유도 | 11.9557 / 93.8595 |
| 양측 p값 | 약 1.4462 × 10⁻²⁰ |
| 첫째 날 − 둘째 날 평균 차이의 조건부 95% 구간 | 15.8453~22.1565분 |
| Mann–Whitney U / 양측 p값 | 2614 / 약 8.8966 × 10⁻¹⁴ |

Mann–Whitney는 분포 차이를 보는 독립표본 순위 검정이다. `method="asymptotic"`와 기본 연속성 보정을 사용했다. 단순한 중앙값 검정으로 해석하지 않으며, 비모수 검정으로 바꿔도 독립성 문제가 해결되지 않는다. [공식 검정 정의](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.mannwhitneyu.html)

**이 표는 인과 효과의 확정적인 유의성 검증이 아니다.** 같은 날 주문은 대기열·조리 자원·직원·재료 상태를 공유한다. 따라서 주문 수 107을 독립 실험 횟수 107로 볼 수 없다. 독립성을 위반하면 p값이 작아지거나 구간이 지나치게 좁아질 수 있다. 현재 자료로 그 정도를 추정해 보정했다고 주장하지 않는다.

p값은 “서비스 개선이 효과 없을 확률”이나 “개선이 원인일 확률”이 아니다. 위 신뢰구간도 전체 가정에 의존하며 관측된 71%의 인과 효과 구간이 아니다. 주문별 단순 부트스트랩 역시 같은 의존 문제를 무시하므로 대표 성과의 보장 구간으로 제시하지 않는다.

## 두 날만으로 분리하기 어려운 효과

인력·숙련도는 비슷했고 둘째 날에는 재료 배송 지연으로 제작이 늦어졌다. 다만 인력 배치·작업속도와 재료 지연의 구간·고객별 영향은 수치로 기록하지 않았다. 둘째 날 수량은 20% 적었고 완료 버튼을 누르는 기준도 같았는지 추가 확인이 필요하다.

`T = α + β × 개선적용 + γ × 둘째날 + ε`를 생각하면, 개선적용이 날짜와 완전히 겹칠 때 두 계수는 따로 식별되지 않는다. 실제로는 기능별 적용 시각도 없어 처치 변수를 정확히 만들기 어렵다. 시간대·수량을 회귀에 넣는 것만으로 이 문제나 누락 요인, 공유 대기열의 의존성이 사라지지 않는다.

일 단위 군집 보정도 하루씩 두 군집뿐이라 신뢰할 만한 일반화된 유의성을 뒷받침하기 어렵다. 임의로 시간을 잘라 표본 수를 늘려 독립 반복 실험처럼 취급하지 않는다. 현재 기록은 남아 있는 이틀의 기술통계로는 유효하지만 이후 행사 전체에 대한 무작위 표본이나 비교 실험은 아니다.

## 결론

> 운영 경험에 따라 고객 UI와 관리자 업무를 개선하고, 이틀간 107건의 기록에서 둘째 날 접수→완료 처리 평균 시간이 26.9분에서 7.9분으로 약 71% 감소한 결과를 확인했다. 중앙값·상위 시간 지표와 짧은 기록 제외·동일 수량·공통 시간대 비교에서도 감소 방향이 유지됐다. 결과는 개선 방향을 지지하는 관측 근거이며, 날짜별 운영 조건을 분리한 서비스 개선의 단독 인과 효과로 확정하지 않았다.

결론은 기록상 완료 처리시간이 감소했다는 것이다. UI 입력시간·순수 조리시간을 측정한 결과나, 통계적으로 확정한 개선의 단독 효과와는 다르다.

## 다음 운영의 검증 설계

1. UI 입력 시작·접수 저장·입금 확인·음식 준비·실제 전달 시각을 구분하고 목표 지표를 사전에 정한다. 포트폴리오의 완료 처리 시각과 실제 준비시간을 구별한다.
2. 개선 버전·배포 시각·기기 역할·인력·재료 지연 구간·주문 수량·유입량을 기록한다. 키오스크 개인정보와 접근 범위는 제한한다.
3. 가능하면 안전하고 동등한 기능 차이에 한해 여러 독립된 운영 단위에 무작위 배정한다. 동일 대기열을 공유하는 두 태블릿을 독립 실험군으로 간주하지 않는다. 교차 적용은 대기열 잔류·학습 효과·워시아웃을 함께 설계한다.
4. 무작위 배정이 어렵다면 여러 운영일·비교 가능한 미적용 환경·충분한 전후 시계열을 확보하고 가정과 함께 분석한다. 단일 이틀 비교에서 자동으로 차이의 차이 분석·중단 시계열이 성립한다고 주장하지 않는다.
5. 변동성·업무상 의미 있는 최소 차이·군집 내 상관을 바탕으로 표본 수를 설계한다. 결과를 본 뒤 유리한 지표·제외 기준·검정 방향을 선택하지 않는다. 검정의 분석 단위와 군집 단위를 일치시킨다.

## 재현 방법과 공개 범위

기술통계는 [Node 분석 코드](../scripts/analyze-operation-days.mjs), 탐색 검정과 조건별 비교는 [Python 분석 코드](../scripts/explore-operation-statistics.py)를 사용한다. Python은 분석용 NumPy·SciPy 1.11 이상과 Node 실행 환경이 필요하며 운영 서버 런타임 의존성에 추가하지 않았다. 실행 결과에는 사용한 라이브러리 버전도 출력한다.

재현 환경은 NumPy 1.26.4·SciPy 1.16.1이었다. 기존 집계·Welch 수치·음식 1개 표본 47건/42건·공통 시간대의 감소 방향을 대조했고, 표본 부족 시 검정 생략과 허용되지 않은 입력 거부도 합성 입력으로 확인했다. 정확한 동일 버전 재현이 필요하면 별도 분석 환경에서 이 버전을 사용한다.

```sh
node scripts/analyze-operation-days.mjs verification/two-day-minimal.local 2026-10-06 2026-10-07
python scripts/explore-operation-statistics.py verification/two-day-minimal.local 2026-10-06 2026-10-07
```

입력은 `createdAt`, `completedAt`, `quantity`, `total`, `resendRequests`만 허용한다. 기존 Node 스크립트의 스키마 검증을 재사용하고 출력에는 집계만 남긴다. 실제 상세 입력은 비공개 로컬 파일이므로 외부 독자는 자기 자료·합성 자료로 방법을 재현할 수 있지만, 공개 원본으로 이 실적을 독립 감사할 수는 없다. 분석으로 주문·문자·배포 상태를 변경하지 않는다.
