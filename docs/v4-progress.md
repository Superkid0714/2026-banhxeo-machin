# V4 1차 보완

추가 운영 정책 변경: 사용자가 모든 주문의 전화번호 수집을 필수로 지정했다. 문자 알림은 기존 선택을 유지한다. 클라이언트 snapshot·route guard·API 모두 전화번호와 동의를 요구하며 건너뛰기 UI를 제거했다. V4 문서 §28의 미사용 시 phone=NULL 정책은 현재 구현에 적용되지 않는다. 검증은 단위 7개·API 4개로 확대했다.

2026-10-02. 고객 Figma 화면과 React/Vite 스택을 유지하며 주문 제출 경계를 보완했다.

## 적용

- `expectedUnitPrice`를 불변 snapshot에 포함하고 서버가 다르면 PRICE_CHANGED를 반환한다. 가격 오류 시 주문·번호·재고를 변경하지 않는다.
- 제출 전 sessionStorage에 payload와 requestId를 기록한다. 저장에 실패하면 API를 호출하지 않는다.
- 모든 제출은 `/api/submissions/:requestId`로 기존 결과를 먼저 확인한다. 404이면 같은 키로 POST한다. timeout·조회 오류는 주문 부재로 해석하지 않는다.
- 불명확한 결과 동안 수정·새 주문 시작을 막는다. 새로고침 후에도 review로 복귀해 같은 snapshot을 재시도한다. 제출을 자동 재전송하지 않는다.
- 성공 시 저널을 서버 Order 응답으로 교체하고 원문 전화번호·동의를 포함한 draft를 삭제한다. 홈 접근 시 고객 입력을 초기화한다.
- 결과 화면 조회 오류는 홈 이동을 유발하지 않는다. 마지막 서버 응답을 유지하고 5초마다 재조회한다.
- 실제 네트워크 요청의 10초 timeout을 추가했다. 오류 전용 UI는 추가하지 않았다.

## 검증

- TypeScript와 production build 통과.
- 단위 테스트 7개: snapshot, SMS 조건, 모든 주문의 전화번호 필수 검증, 저널 재생성, 성공 후 원문 삭제, 기존 주문 복구, 조회 장애 시 POST 금지.
- API 테스트 4개: 결과 재조회·키 충돌, 50개 동일 키 요청·가격 불일치 거부·번호 무변경, 동의 없는 SMS 거부, 문자 미사용 주문의 전화번호·동의 검증.
- 브라우저: SMS 주문 생성, 결과 URL 새로고침, 다음 고객 알림 선택 초기화와 전화번호 빈 값 확인.
- 응답 유실은 서비스 의존성을 주입한 테스트로 검증했다. 실제 회선 장애 주입 테스트는 아직 수행하지 않았다.

## 남은 범위

개발 서버와 Railway 배포 서버는 같은 메모리 기반 데모 API를 사용한다. 서버 재시작 후에는 기존 주문 조회가 404가 되어 클라이언트의 같은 키 재요청도 새 주문을 만들 수 있다. 다중 프로세스·DB 정합성을 보장하지 않는다. sessionStorage는 같은 탭 새로고침을 지원하며 탭 종료·삭제에는 대응하지 않는다.

요청 결과가 불명확한 저널에는 복구를 위해 전화번호가 일시 보관된다. 운영에서는 Kiosk 인증·접근 통제·보관 및 삭제 정책을 연결해야 한다. 새로운 조회 API도 현재 인증된 운영 API가 아니다.

다음 단계는 PostgreSQL/Supabase 테이블·UNIQUE/CHECK/RLS, Event Session/Kiosk 인증, 원자적 주문 생성 RPC다. 주문 상태와 결제 상태 분리, 자동취소/복원, 관리자, SMS Outbox·Lease/Fencing은 미구현이다. DB 접속 설정과 검증 환경을 연결한 뒤 서버 재시작·재고 경쟁·보안 테스트가 필요하다.
