# 배포 상태와 운영 절차

확인 기준일: 2026-11-26, 한국 시간. [운영 기록](operations-record.md)과 [기술 종합](technical-reference.md)을 함께 참고한다. 이 문서의 명령은 절차 설명이며, 문서 작성만으로 재배포나 DB 변경을 수행하지 않는다.

## 확인된 배포와 저장소 차이

운영 서비스는 [festival-customer-order](https://festival-customer-order-production.up.railway.app/), 관리자 경로는 `/admin`이다. Railway 최근 배포 `4e2318ee-d4d6-4ec7-b270-caa58cf55ae0`는 `SUCCESS`이며 `/health`가 HTTP 200과 `{"status":"ok"}`를 반환했다. HTML에서 제공 중인 화면은 `/assets/index-9SXvIk_H.js`다.

이 ID와 파일은 10월 7일 현장 개선 배포에서 확인한 것과 같다. 당시 새 고객은 접수 성공 후 홈으로 돌아가고 개인정보·입금은 별도 화면이며, 관리자 전체 번호·픽업 재발송·한 문장 대기시간 안내를 확인했다. 이번에는 고객 흐름으로 새 실제 주문을 만들거나 문자를 재전송하지 않았다.

| 항목 | 저장소 상태 | 현재 운영 적용 판단 |
| --- | --- | --- |
| 현장 고객·관리자·예측 개선 | 10월 7일 기능별 커밋에 정리 | 당시 CLI 배포 및 화면 확인 기록 있음 |
| 실제 계좌의 소스 제거·환경 변수화 | `7ba26bf` 이후 소스 | 이후 소스 정리이므로 동일 배포에 반영됐다고 단정하지 않음 |
| 운영 후 점검 개선: 미사용 단계·조회·고정 지연·예약 계약 | 11월 26일 `da381a3`에 구현·로컬 검증 | 최근 배포가 그대로이므로 미배포 |
| 이번 종합 문서 | 11월 26일 문서 변경 | 런타임 변경 없음 |

CLI가 작업 폴더를 업로드한 배포와 GitHub 커밋을 일대일로 연결하는 검증된 release manifest는 없다. 배포 ID·화면 파일·검증한 동작을 근거로 쓰고, 최근 Git 커밋이 곧 운영 코드라고 표시하지 않는다. 향후 빌드에 커밋 SHA·빌드 시각을 넣는 릴리스 메타데이터는 개선 과제다.

운영 중 피드백으로 반영한 UI·시스템 개선과, 운영 이후 실제 흐름·코드를 점검해 발견하고 구현한 개선은 [운영 경험 분석](field-operation-changes.md)에서 구분한다. 이 표의 미배포 표시는 사후 개선의 구현 여부와 운영 적용 여부를 구별하기 위한 것이다.

## 빌드·실행 계약

Node.js 22 환경에서 다음을 실행한다.

```sh
npm ci
npm run build
npm start
```

`build`는 TypeScript 검사, Vite 화면 빌드, esbuild 서버 번들을 수행한다. 화면은 `dist/`, 서버는 `dist-server/start.mjs`에 생성된다. `railway.json`은 RAILPACK, 같은 빌드 명령, 서버 시작 명령, `/health`, 60초 헬스 타임아웃, 인스턴스 1개, 실패 시 최대 3회 재시작을 지정한다.

운영 DB는 `ORDER_DB_PATH`를 우선하고 미설정이면 `RAILWAY_VOLUME_MOUNT_PATH` 또는 `data/` 아래의 `orders.sqlite`를 사용한다. 영구 볼륨이 없으면 재배포 때 데이터가 유지된다고 보장할 수 없다. 기본 `/health`는 프로세스 응답 확인이며 DB 복구·외부 문자·예약 연동의 성공을 대신하지 않는다.

## 설정과 비밀 정보

| 변수·파일 | 용도·주의 |
| --- | --- |
| `ADMIN_USERNAME`, `ADMIN_PASSWORD` | 관리자 계정, 비밀번호 최소 16자. 값은 문서에 기재하지 않음 |
| `ADMIN_COOKIE_SECURE` | 운영 HTTPS에서는 기본 보안 쿠키, `false`는 로컬 HTTP에서만 |
| `PHONE_ENCRYPTION_KEY` | 32바이트 키의 64자리 hex. 기존 DB와 함께 유지 |
| `ORDER_DB_PATH` | 영구 볼륨의 SQLite 파일 경로 |
| `ORDER_API_KEY` | 외부 예약 서비스 서버 인증키 |
| `RESERVATION_LOOKUP_URL` | 11월 소스에서 지원, 미설정 시 기존 운영 주소. HTTPS만 허용 |
| `SOLAPI_API_KEY`, `SOLAPI_API_SECRET`, `SOLAPI_SENDER_NUMBER` | 문자 서비스 키 및 등록 발신번호 |
| `PORT` | Railway가 제공하는 HTTP 포트 |
| `VITE_PAYMENT_BANK`, `VITE_PAYMENT_HOLDER`, `VITE_PAYMENT_ACCOUNT` | 고객 공개용 계좌 안내. 빌드 때 삽입되므로 값 변경 후 재빌드 필요 |
| `public/assets/payment-qr.jpg` | 계좌별 QR. GitHub 제외, 배포 시 별도 공급 |
| `.env.production.local` | 로컬 Vite 빌드의 비공개 값. Git·Railway 업로드에서 제외 |
| `.env.example` | 빈 계좌·예약 URL 예시만 공유. 실제 비밀키 넣지 않음 |

운영 Node 서버는 `.env`를 자동으로 읽지 않는다. 서버 변수는 프로세스 또는 Railway 환경에 설정한다. Vite가 로컬 빌드 환경 파일을 읽는 동작과 구분한다. 개발 Vite API 플러그인의 서버 변수도 실행 프로세스에 공급해야 한다.

`VITE_*`는 브라우저 번들에 들어가므로 비밀키 저장소가 아니다. 계좌 안내를 GitHub에서 제외하는 것과 고객 화면에서 계좌를 숨기는 것은 다른 문제다. 암호화 키를 교체하면 기존 번호 복호화가 실패할 수 있으므로 단순 환경 변수 변경으로 교체하지 않는다.

## 두 가지 배포 입력

**로컬 Railway CLI:** `.railwayignore`가 환경 파일·자격 증명·DB·검증 자료를 제외한다. 계좌 QR은 이 파일에서 제외하지 않으므로 로컬 파일이 있으면 업로드 대상이다. `.gitignore`는 QR을 제외한다. 비공개 파일이 GitHub와 배포 서비스에서 필요한 범위가 서로 다르다.

```sh
railway up --detach --service festival-customer-order --environment production
railway status --json
```

**GitHub 연동 빌드:** 저장소에는 QR이 없으므로 보호된 빌드 입력이나 별도 파일 공급 절차가 필요하다. 실제 계좌 빌드 변수를 설정하고 QR이 최종 `dist/assets/`에 있는지 확인한다. GitHub push만으로 운영 반영됐다고 가정하지 않는다. Railway의 저장소·브랜치 연동 여부와 실제 새 배포를 확인해야 한다.

## 배포 전후 확인

배포 전에는 작업 폴더·커밋을 확인하고, 영구 볼륨·기존 암호화 키·환경 변수·QR을 확인한다. [기술 문서의 검증](technical-reference.md#검증)을 로컬 임시 저장소에서 실행한다. `test:api`의 `TEST_API_URL`이 운영 주소를 가리키지 않도록 한다.

배포 후에는 다음을 순서대로 확인한다.

1. Railway의 새 배포 ID와 `SUCCESS`를 기록한다. 업로드 완료와 서비스 가동 완료는 다르다.
2. `/health` HTTP 200 및 HTML이 가리키는 새 화면 번들, 정적 asset을 확인한다.
3. 고객 직접 경로·판매 중단 안내·연락처·개인정보·입금 화면의 순서를 확인한다. 전체 실주문 테스트가 필요하면 운영자가 승인한 시험 주문의 식별·정리 기준을 정한다.
4. 관리자 미인증 요청이 거부되고 로그인 후 보드·이력·전체 번호가 정상인지 확인한다. 실제 번호·스크린샷은 공개 로그에 남기지 않는다.
5. `da381a3` 배포라면 보드의 이력 제외 조회, 판매 가능 여부 전용 조회, 예약 6자리 형식, 과거 링크 호환을 확인한다. 외부 실예약·문자를 무단 사용하지 않는다.
6. 관리자 화면의 예측은 한 줄이어야 한다. 소스의 계산 방식과 현재 학습 지표를 별도로 확인한다.

HTML은 `no-store`, 정적 파일은 1시간 캐시다. 이전 설명이 보이면 열린 탭의 오래된 실행 코드일 수 있으므로 새로고침하고 HTML의 asset과 배포 ID를 대조한다. 캐시라고 단정하기 전에 실제 배포본부터 확인한다.

## 장애 대응과 데이터 보존

| 증상 | 확인·대응 |
| --- | --- |
| 접수 응답 불명확 | 같은 탭의 제출 복구로 기존 요청을 조회. 임의 새 키로 반복 생성하지 않음 |
| 관리자 세션 만료 | 다시 로그인. 서버 재시작은 메모리 세션을 초기화함 |
| 문자 실패·불명 | 요청 접수·전달·실패를 구분하고 진행 중 재요청을 피함. 확인 후 허용된 관리자 재발송 사용 |
| 계좌·QR 누락 | 빌드 변수와 QR의 배포 입력을 확인. Git 소스만으로 QR이 생기지 않음 |
| DB 또는 번호 복호화 오류 | 기존 볼륨·경로·암호화 키 일치 여부 확인. 운영 DB를 새 빈 DB로 덮어쓰지 않음 |
| 예약 접수 실패 | 코드 형식, 한국 날짜·입금, 접수 중단, 서버 전용 키·HTTPS endpoint·외부 오류 확인 |
| 예측이 현장과 다름 | 완료 시점 기록, 입금·고객 방문 지연, 오래된 행사 데이터, 현재 미완료 수량 확인 |
| 롤백 필요 | 이전 실행 버전과 새 데이터의 호환 여부 확인. 코드 롤백과 DB 복원을 별개로 판단 |

SQLite WAL 사용 중 메인 DB 파일 하나만 임의 복사하면 안전한 백업이라고 볼 수 없다. 일관된 SQLite 백업 또는 정지된 상태의 검증된 보관 절차가 필요하다. 백업·암호화 키는 접근을 제한해 따로 관리하고 복원은 별도 환경에서 먼저 검증한다. 이 저장소에는 자동 백업·복원 리허설의 완료 증거가 없으므로 구축됐다고 기록하지 않는다.

취소·이력 영구 삭제는 통계와 고객 조회에 영향을 준다. 완료 주문을 보드에서 정리하는 목적이면 삭제 대신 보관을 사용한다. 존재하지 않는 처리 시각을 사후 생성해 운영 실적과 API 이력을 억지로 맞추지 않는다.

## 릴리스 기록 항목
