## 운영 결과와 집계 경계

2026-11-26 관리자 API의 전체 이력을 조회해 합계만 계산했다. 주문 서버에서 확인되는 107건은 모두 `paid`·`completed`였다. 삭제된 주문은 이력에 없으므로 이 수치가 행사 중 모든 시도·취소를 복원하는 원장은 아니다.

| 근거 | 주문·수령 건수 | 음식 수량 | 결제 확인 금액 |
| --- | ---: | ---: | ---: |
| 주문 서버 API에 남은 완료 기록 | 107건 | 126개 | 755,000원 |
| 별도 사전예약 수령: 이전 운영자 확인 기록 | 2건 | 2개 | 11,000원 |
| 중복 제외 행사 전체 합계 | **109건** | **128개** | **766,000원** |

주문 서버의 107건에는 이미 사전예약 1건·2개·11,000원이 포함돼 있다. 이 예약을 다시 더하지 않는다. API 합계에서 이를 제외하면 현장 주문은 106건·124개·744,000원이며, 운영자 확인 2건까지 포함한 전체 사전예약은 3건·4개·22,000원이다. 현장 단가 6,000원과 예약 단가 5,500원으로 계산 결과가 일치한다.

추가 예약 2건은 이전 운영자 확인을 README와 `da381a3` 커밋에 기록한 사실을 근거로 한다. 이번에는 외부 예약 서비스 원장을 다시 대조하지 않았다. 없는 수령 시각이나 주문 이력을 운영 DB에 소급 생성하지 않았다. 이번 행사 환불은 없었다는 운영 기록을 유지하며 현재 API에도 환불 상태는 없다. 비용 자료가 없으므로 **순이익·마진·비용은 계산하지 않는다**.

## 운영 중 경험으로 개선한 UI와 시스템

운영자는 실제 장사 중 접수 병목 때문에 UI를 바꿨고, 관리자 화면을 사용해 보면서 재발송·전체 전화번호가 필요해졌다고 설명했다. 아래는 그 피드백에 따라 운영 중 적용한 변경이다. UI는 필요한 입력·안내를 찾고 끝내는 문제를, 시스템은 상태·연락·보관·예측 업무를 지원하는 문제를 다뤘다. 상세 원인과 변경의 연결은 [운영 경험 분석](field-operation-changes.md#운영-중-ui-개선의-분석)에 있다.

운영자는 **태블릿 2대로 운영했다**고 추가 확인했다. 두 서비스 연동 문제와 두 기기의 동시 처리 충돌은 구분한다. 현재 대응은 서버의 주문·설정 버전 검사, SQLite 트랜잭션, 요청 키·예약 ID 중복 방지, 충돌 안내 뒤 최신 조회다. 관리자 화면은 5초 폴링이며 즉시 동기화는 아니다. 구체적인 당시 오류·기기별 역할·발생 횟수는 확인되지 않았다. 동작 예시·현재 대응·운영 절차·남은 한계는 [태블릿 2대 운영 기록](field-operation-changes.md#태블릿-2대-운영과-동시-처리-충돌-대응)에 정리했다.

| 현장 문제·요청 | 변경 | 적용 범위와 한계 |
| --- | --- | --- |
| 고객이 불필요한 선택·확인 화면에서 머뭄 | 이용 방법, 추가 최종 확인, 제출 직후 완료 화면 제거. 성공하면 홈으로 복귀 | 현장 개선 배포에 반영. 처리시간 단축률은 미측정 |
| 단계 축소 과정에서 개인정보와 계좌 확인을 합치면 목적이 혼동됨 | 전화번호 → 개인정보 동의 → 입금 안내를 별도 화면으로 유지 | 고객의 필수 동의·입금 확인을 유지 |
| 문자 한 번으로 고객이 바로 오지 않음 | 수령완료 카드·상세에서도 픽업 문자 재발송 | 발송 처리 중 중복 요청 차단. 재발송이 실제 방문을 보장하지 않음 |
| 마스킹 번호로는 고객 연락·주문 대조가 어려움 | 인증된 관리자에게 전체 전화번호와 검색 제공 | 고객 응답은 마스킹 유지. 번호 없는 예약은 미등록 |
| 관리자가 너무 많은 상태 버튼을 처리해야 함 | 결제확인 → 조리중 → 수령완료로 단순화 | 실제 전달과 픽업 안내 시점이 혼재하는 명칭 문제는 남음 |
| 끝난 주문이 보드에 남음 | 처리 완료·내역 이동으로 보드에서 제외하고 이력 보존 | 취소·영구 삭제와 다른 동작 |
| 취소 주문을 집계에서 빼야 함 | 확인 후 목록·이력 삭제 및 금액·수량 집계 제외 | 삭제된 원래 사건을 현 이력만으로 복원할 수 없음 |
| 새 고객이 얼마나 기다려야 하는지 질문 | 현재 대기 음식 수량과 과거 완료 시간으로 새 음식 1개 예측 | 입금 확인·기록 지연 영향 포함 |
| 관리자에게 예측 설명·범위가 너무 많음 | “지금 주문하면 약 ○분” 한 문장만 표시 | 내부 오차·범위는 유지. 표시 단순화와 정확도 향상은 다름 |

## 주문과 운영 상태를 읽는 방법

현장 접수는 **상품·수량 → 전화번호 → 개인정보 동의 → 입금 안내·접수 → 홈**이다. 주문 접수는 입금 완료가 아니다. 직원이 실제 입금을 확인하면 조리중으로 옮기고 결제 안내 문자를 요청한다. 사전예약은 서버가 입금·수령일·수량을 확인한 뒤 조리중으로 접수한다.

현재 수령완료 변경은 픽업 문자 요청도 수행한다. 고객이 아직 오지 않은 주문에 재발송이 필요한 운영 관행이 있으므로 `completed`를 물리적 전달의 정확한 시점이라고 가정하지 않는다. `finishedAt`은 이후 처리 완료·이력 보관 시각이다. 이 차이는 운영 통계와 예측 학습에도 영향을 준다.

판매 중단은 새 현장·예약 접수를 막고 기존 주문 처리는 유지한다. 기본 설정은 재고 추적 비활성·결제 제한 시간 0분이다. 재고 추적을 켠 경우 결제 전 취소는 예약된 재고를 복원하지만 조리 시작 후 취소는 복원하지 않는다. 설정·상태 변경은 버전 충돌을 검사한다.

| 11월 26일 접수 당시 예측과 실제 완료 비교 | 최근 완료 20건 | **3.6분** |

현재 모델의 과거 검증 오차는 비교 기준보다 약 12.5% 작다. 서로 다른 시점의 표본으로 나온 4.9분과 3.5분 차이를 UI 변경이나 모델 구조 변경의 인과 효과로 해석하지 않는다. 검증 오차는 성공 확률이나 보장 시간 범위가 아니다. 운영 검증은 저장된 접수 당시 예측값을 사용하며 화면의 5분 단위 반올림 문구와 직접 비교한 지표는 아니다.

학습은 최신 최대 80건, 최근성 반감기 120분의 비음수 가중 회귀다. 반감기는 가장 최근 완료 기록과의 시간 차이를 기준으로 하며, 실제 현재 시각에서 2시간이 지났다고 모델 전체가 자동 폐기되는 구조는 아니다. 데이터가 오래돼도 현재 UI는 단순 예상값을 표시하므로 다음 행사에 그대로 신뢰하지 말고 새 운영 데이터로 검증해야 한다.

## 확인 범위와 공개 범위

이번에는 공개 사이트의 상태, Railway 배포 ID, 인증된 관리자 API의 비식별 합계를 조회했다. 관리자 로그인·로그아웃 외에 주문 변경·문자 재발송·설정 변경·재배포를 실행하지 않았다. API에서 현재 삭제된 주문과 별도 예약 원장을 복원할 수는 없다.

관련 코드의 자동 검증 범위와 운영 절차는 [기술 종합](technical-reference.md#검증) 및 [배포·운영 절차](deployment-runbook.md)를 따른다. 운영 원본·스크린샷·검증 로그는 공개 문서에 첨부하지 않는다.
