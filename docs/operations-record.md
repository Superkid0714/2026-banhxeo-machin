분석 대상은 운영 서버에 남은 주문 이력과 별도로 확인한 예약 수령 건이다. 집계와 배포 상태는 2026-11-26에 대조했다. 기능 코드는 `da381a3` 기준이며, 뒤에 추가한 문서 커밋과 운영 배포본은 별개다.

개인 개발 프로젝트로 고객·관리자 화면, 서버·DB·인증, 문자·예약 연동, 예측 모델과 배포를 직접 맡았다. 소개와 문제 해결 과정은 [포트폴리오](portfolio.md)에 정리했다.

## 운영 결과와 집계 경계

2026-11-26 관리자 API의 전체 이력을 조회해 합계만 계산했다. 주문 서버에서 확인되는 107건은 모두 `paid`·`completed`였다. 삭제된 주문은 이력에 없으므로 이 수치가 행사 중 모든 시도·취소를 복원하는 원장은 아니다.

| 근거 | 주문·수령 건수 | 음식 수량 | 결제 확인 금액 |
| --- | ---: | ---: | ---: |
| 주문 서버 API에 남은 완료 기록 | 107건 | 126개 | 755,000원 |
| 별도 사전예약 수령: 이전 운영자 확인 기록 | 2건 | 2개 | 11,000원 |
| 중복 제외 행사 전체 합계 | **109건** | **128개** | **766,000원** |

주문 서버의 107건에는 이미 사전예약 1건·2개·11,000원이 포함돼 있다. 이 예약을 다시 더하지 않는다. API 합계에서 이를 제외하면 현장 주문은 106건·124개·744,000원이며, 운영자 확인 2건까지 포함한 전체 사전예약은 3건·4개·22,000원이다. 현장 단가 6,000원과 예약 단가 5,500원으로 계산 결과가 일치한다.

추가 예약 2건은 이전 운영자 확인을 README와 `da381a3` 커밋에 기록한 사실을 근거로 한다. 이번에는 외부 예약 서비스 원장을 다시 대조하지 않았다. 없는 수령 시각이나 주문 이력을 운영 DB에 소급 생성하지 않았다. 이번 행사 환불은 없었다는 운영 기록을 유지하며 현재 API에도 환불 상태는 없다. 비용 자료가 없으므로 **순이익·마진·비용은 계산하지 않는다**.

## 이틀 운영의 수치 비교

### 핵심 관측 성과

실제 운영 피드백에 따라 주문 UI·관리자 기능을 개선하는 과정에서 **둘째 날 주문 접수→완료 처리 평균 시간이 첫째 날 대비 약 71% 감소**했다. 인력과 숙련도는 이틀간 비슷했고 둘째 날에는 재료 배송 지연으로 제작이 늦어졌다. 지연 구간은 기록하지 않아 평균에 미친 영향을 따로 계산하지는 못했다.

| 지표 | 2026-10-06 | 2026-10-07 |
| --- | ---: | ---: |
| API에 남은 주문·완료 기록 | 58건 | 49건 |
| 음식 수량 | 70개 | 56개 |
| 결제 확인 금액 | 419,000원 | 336,000원 |
| 접수→완료 처리 평균 | 26.9191분 | 7.9182분 |

| 문자 재안내 요청 이력 | 0회 | 20회 |

### 성과 지표 전체와 단위

| 지표 | 첫째 날 | 둘째 날 | 차이·해석 |
| --- | ---: | ---: | --- |
| 접수→완료 평균 | 26.9191분 | 7.9182분 | 19.0009분·70.5853% 감소 |
| 같은 시간 중앙값 | 29.0910분 | 8.0346분 | 72.3813% 감소 |
| 같은 시간 90백분위수 | 38.9532분 | 15.3767분 | 60.5252% 감소 |
| 15분 초과 | 49/58건·84.4828% | 6/49건·12.2449% | 72.2379%p 감소 |
| 30분 초과 | 26/58건·44.8276% | 1/49건·2.0408% | 42.7868%p 감소 |
| 음식 1개 평균 | 47건·26.4187분 | 42건·7.4167분 | 71.9262% 감소 |
| 15초~120분 표본 평균 | 58건·26.9191분 | 47건·8.2474분 | 69.3623% 감소 |
| 문자 재안내 요청 | 0회 | 20회 | 20회 증가. 초기값 0이므로 증가율 계산하지 않음 |
| 주문 건수 | 58건 | 49건 | 15.5172% 감소. 비교 조건 |
| 음식 수량 | 70개 | 56개 | 20% 감소. 비교 조건 |

15분·30분 초과는 사후 탐색 지표다. 비율의 분모는 음수가 아닌 완료 소요시간이 계산되는 주문 수이며 이번에는 58건·49건 모두 해당했다. `소요시간 > 기준분`을 사용하고 경계값은 초과에 포함하지 않는다. `%p 감소 = 첫째 날 초과 비율 - 둘째 날 초과 비율`로, 상대 감소율 `%`와 구분한다. 요청 건수 20회는 고객 20명·문자 전달 성공 20건·방문 20회를 뜻하지 않는다.

주문 건수·수량·금액 감소는 개선 성과가 아니라 운영 조건이다. 중앙값·상위 시간·임계값 초과·수량별 비교는 같은 주문에서 파생한 상관된 결과이며 각각 독립적인 인과 증거가 아니다. 소수 넷째 자리 수치는 계산 대조용으로, 포트폴리오에서는 과도한 정밀도를 피하고 약 71%, 42.8%p처럼 표시한다.

평균 차이는 약 19.0분이며 감소율은 `(26.9190663793 - 7.9181523810) / 26.9190663793 × 100 = 약 70.6%`다. 포트폴리오에서는 반올림해 **약 71%**로 표시한다. 중앙값은 약 72.4%, 90백분위수는 약 60.5% 감소했다. 수량은 20%, 주문 건수는 약 15.5% 감소했으므로 처리량 증가나 매출 증가로 표현하지 않는다.

### 지표 정의와 재현 기준

로컬 최소 입력으로 동일 계산을 수행하는 [공유 분석 코드](../scripts/analyze-operation-days.mjs)와 [실행 방법·입력 추출 규칙](engineering-decisions.md#71-관측-성과의-재현)을 추가했다. 네트워크나 관리자 자격 증명은 사용하지 않고, 날짜별 집계만 출력한다. 상세 입력은 `verification/`에 비공개 보관하며 원본 고객 응답을 커밋하지 않는다.

관리자 API 전체 이력을 읽기 조회해 계산했다. 한국 시간의 `createdAt` 날짜로 나누고, 각 주문에서 첫 `조리 완료…` 또는 정확히 `수령 완료` 이력 시각을 찾아 `완료 이력 시각 - createdAt`을 분으로 계산했다. 이번 107건은 모두 첫 대상 이벤트가 `수령 완료`였다. `finishedAt`의 보관 시각과 혼동하지 않는다. 백분위수는 정렬한 n건의 `ceil(n × p)`번째 값, 평균은 주문별 시간의 단순 평균으로 계산한다. 음식 개수로 가중하지 않는다.

핵심 71%는 API에 남은 **107건 전부를 제외 없이** 사용했다. 둘째 날 15초 미만의 기록 2건도 임의로 테스트 주문이라 간주해 빼지 않았다. 모델 학습과 같은 유효 시간 15초~120분 기준을 적용한 보조 비교에서는 첫째 날 58건 평균 26.92분, 둘째 날 47건 평균 8.25분으로 약 69.4% 감소한다. 제외 기준을 적용해도 방향은 같지만 주된 수치와 표본을 혼용하지 않는다.

시간 기록이 없는 운영자 확인 예약 2건은 전체 매출·수량에는 별도 반영하되 이 날짜별 소요시간 비교에는 포함하지 않았다. 삭제된 주문도 복원할 수 없어 비교 대상에 없다. 첫째 날 58건에는 예약 1건·2개가 포함되고 둘째 날 49건에는 예약 접수 주문이 없다.

### 개선과 연결해 해석할 수 있는 부분

서비스에는 불필요한 선택·확인·완료 단계 제거와 홈 복귀, 직원의 재연락을 위한 픽업 재발송, 전체 번호 조회, 상태·보관 흐름 개선이 반영됐다. 재안내 요청이 둘째 날 20회 남아 있어 추가 기능이 실제 업무에 사용됐음을 확인한다. 평균뿐 아니라 중앙값과 상위 시간 지표도 낮아졌다는 점을 함께 제시한다.

인력·숙련도는 유사했고 둘째 날에는 재료 지연이 있었다. 다만 지연 구간과 고객별 영향, 기기별 역할이나 작업속도의 수치 기록은 남아 있지 않다.

### 성과 표현의 경계

사후 업무 가설, 독립표본을 가정한 Welch·순위 검정, 주문 단위 의존성과 날짜별 교란, 동일 수량·시간대 비교는 [별도 통계 문서](statistical-review.md)에 정리했다. 작은 p값을 개선 효과의 확정적 증거로 채택하지 않는다. 대표 수치는 여전히 기록 전체에서 계산한 평균 감소율이다.

운영 중 서비스를 개선했고 둘째 날 접수→완료 처리 평균은 약 71% 짧아졌다. UI 입력시간·순수 조리시간·실제 고객 수령시간의 변화는 별도로 측정하지 않았다.

완료 상태가 픽업 안내 요청과 연결돼 있으므로 두 날짜의 버튼을 누르는 기준이 같았는지는 추가 확인이 필요하다. 음식 수량·시간대별 유입 차이와 개선 기능별 정확한 적용 시점도 통제하지 않았다. 특히 재료 배송 지연이 고객 주문 접수 이전에 끝났다면 해당 지연은 이 지표에 포함되지 않을 수 있다. 전체 71%를 서비스 개선만의 원인으로 단정하거나 재료 지연을 보정한 순효과라고 주장하지 않는다. 11월 운영 후 코드 최적화는 미배포이므로 10월 이틀의 성과 원인으로 포함하지 않는다.

## 운영 중 경험으로 개선한 UI와 시스템

실제 장사 중 접수 병목을 겪어 UI를 바꿨고, 관리자 화면을 쓰면서 재발송·전체 전화번호 조회를 추가했다. 아래는 그 피드백에 따라 운영 중 적용한 변경이다. UI는 필요한 입력·안내를 찾고 끝내는 문제를, 시스템은 상태·연락·보관·예측 업무를 지원하는 문제를 다뤘다. 상세 원인과 변경의 연결은 [운영 경험 분석](field-operation-changes.md#운영-중-ui-개선의-분석)에 있다.

태블릿은 2대로 운영했다. 두 서비스 연동 문제와 두 기기의 동시 처리 충돌은 구분한다. 현재 대응은 서버의 주문·설정 버전 검사, SQLite 트랜잭션, 요청 키·예약 ID 중복 방지, 충돌 안내 뒤 최신 조회다. 관리자 화면은 5초 폴링이며 즉시 동기화는 아니다. 구체적인 당시 오류·기기별 역할·발생 횟수는 확인되지 않았다. 동작 예시·현재 대응·운영 절차·남은 한계는 [태블릿 2대 운영 기록](field-operation-changes.md#태블릿-2대-운영과-동시-처리-충돌-대응)에 정리했다.

| 현장 문제·요청 | 변경 | 적용 범위와 한계 |
| --- | --- | --- |
| 고객이 불필요한 선택·확인 화면에서 머뭄 | 이용 방법, 추가 최종 확인, 제출 직후 완료 화면 제거. 성공하면 홈으로 복귀 | 현장 개선 배포에 반영. UI 입력시간 단축률은 미측정 |
| 단계 축소 과정에서 개인정보와 계좌 확인을 합치면 목적이 혼동됨 | 전화번호 → 개인정보 동의 → 입금 안내를 별도 화면으로 유지 | 고객의 필수 동의·입금 확인을 유지 |
| 문자 한 번으로 고객이 바로 오지 않음 | 수령완료 카드·상세에서도 픽업 문자 재발송 | 발송 처리 중 중복 요청 차단. 재발송이 실제 방문을 보장하지 않음 |
| 마스킹 번호로는 고객 연락·주문 대조가 어려움 | 인증된 관리자에게 전체 전화번호와 검색 제공 | 고객 응답은 마스킹 유지. 번호 없는 예약은 미등록 |
| 관리자가 너무 많은 상태 버튼을 처리해야 함 | 결제확인 → 조리중 → 수령완료로 단순화 | 실제 전달과 픽업 안내 시점이 혼재하는 명칭 문제는 남음 |
| 끝난 주문이 보드에 남음 | 처리 완료·내역 이동으로 보드에서 제외하고 이력 보존 | 취소·영구 삭제와 다른 동작 |
| 취소 주문을 집계에서 빼야 함 | 확인 후 목록·이력 삭제 및 금액·수량 집계 제외 | 삭제된 원래 사건을 현 이력만으로 복원할 수 없음 |
| 새 고객이 얼마나 기다려야 하는지 질문 | 현재 대기 음식 수량과 과거 완료 시간으로 새 음식 1개 예측 | 입금 확인·기록 지연 영향 포함 |
| 관리자에게 예측 설명·범위가 너무 많음 | “지금 주문하면 약 ○분” 한 문장만 표시 | 내부 오차·범위는 유지. 표시 단순화와 정확도 향상은 다름 |

## 운영 이후 점검으로 발견하고 개선한 사항

행사 뒤 코드를 다시 보며 정리한 내용이다. 구현과 로컬 검증은 마쳤지만 아직 운영에 재배포하지 않았다. 상세 분석은 [운영 이후 개선](field-operation-changes.md#운영-이후-점검으로-발견한-개선)에 있다.

| 발견한 개선점 | 변경 | 적용 범위와 한계 |
| --- | --- | --- |
| 화면 선택을 지워도 미사용 코드가 남음 | `NotificationChoice`, 이전 단계 타입·프레임 제거, 경로 결정 함수 분리 | 운영 후 소스 정리, 미배포 |
| 판매 가능 여부 조회가 전체 주문 처리까지 수행 | 설정 전용 조회로 분리 | 운영 후 소스 정리, 미배포. DB 전체 JSON 읽기 자체는 남음 |
| 관리자 보드가 매번 모든 이력을 전송 | 보드 조회는 이력 제외, 이력 화면만 전체 조회 | 운영 후 소스 정리, 미배포. 서버 측 전체 학습 이력 계산은 유지 |
| 신규 주문 응답에 고정 대기 존재 | 저장 뒤 800ms 고정 지연 제거 | 운영 후 소스 정리, 미배포. 전체 응답 지연을 800ms 보장 단축한다는 뜻은 아님 |
| 화면·서버의 예약 코드 길이 규칙 불일치 | 6자리 숫자로 통일, 잘못된 형식은 외부 호출 전 차단 | 운영 후 소스 정리, 미배포 |

## 주문과 운영 상태를 읽는 방법

현장 접수는 **상품·수량 → 전화번호 → 개인정보 동의 → 입금 안내·접수 → 홈**이다. 주문 접수는 입금 완료가 아니다. 직원이 실제 입금을 확인하면 조리중으로 옮기고 결제 안내 문자를 요청한다. 사전예약은 서버가 입금·수령일·수량을 확인한 뒤 조리중으로 접수한다.

현재 수령완료 변경은 픽업 문자 요청도 수행한다. 고객이 아직 오지 않은 주문에 재발송이 필요한 운영 관행이 있으므로 `completed`를 물리적 전달의 정확한 시점이라고 가정하지 않는다. `finishedAt`은 이후 처리 완료·이력 보관 시각이다. 이 차이는 운영 통계와 예측 학습에도 영향을 준다.

판매 중단은 새 현장·예약 접수를 막고 기존 주문 처리는 유지한다. 기본 설정은 재고 추적 비활성·결제 제한 시간 0분이다. 재고 추적을 켠 경우 결제 전 취소는 예약된 재고를 복원하지만 조리 시작 후 취소는 복원하지 않는다. 설정·상태 변경은 버전 충돌을 검사한다.

## 대기시간 모델의 검증 기록

| 시점·방법 | 표본 | 평균 절대 오차 |
| --- | --- | ---: |
| 초기 기록의 과거 순차 검증 | 학습 기록 58건, 검증 20건 | 모델 4.9분 / 최근 10건 평균 7.4분 |
| 11월 26일 운영 API의 과거 순차 검증 | 최신 유효 학습 기록 80건, 검증 20건 | 모델 3.5분 / 최근 10건 평균 4.0분 |
| 11월 26일 접수 당시 예측과 실제 완료 비교 | 최근 완료 20건 | **3.6분** |

현재 모델의 과거 검증 오차는 비교 기준보다 약 12.5% 작다. 서로 다른 시점의 표본으로 나온 4.9분과 3.5분 차이를 UI 변경이나 모델 구조 변경의 인과 효과로 해석하지 않는다. 검증 오차는 성공 확률이나 보장 시간 범위가 아니다. 운영 검증은 저장된 접수 당시 예측값을 사용하며 화면의 5분 단위 반올림 문구와 직접 비교한 지표는 아니다.

학습은 최신 최대 80건, 최근성 반감기 120분의 비음수 가중 회귀다. 반감기는 가장 최근 완료 기록과의 시간 차이를 기준으로 하며, 실제 현재 시각에서 2시간이 지났다고 모델 전체가 자동 폐기되는 구조는 아니다. 데이터가 오래돼도 현재 UI는 단순 예상값을 표시하므로 다음 행사에 그대로 신뢰하지 말고 새 운영 데이터로 검증해야 한다.

## 확인 범위와 공개 범위

공개 사이트·Railway 배포 정보와 관리자 API 집계를 읽기 조회했다. 주문·문자·설정은 변경하지 않았다. API에서 현재 삭제된 주문과 별도 예약 원장을 복원할 수는 없다.

관련 코드의 자동 검증 범위와 운영 절차는 [기술 종합](technical-reference.md#검증) 및 [배포·운영 절차](deployment-runbook.md)를 따른다. 운영 원본·스크린샷·검증 로그는 공개 문서에 첨부하지 않는다.
